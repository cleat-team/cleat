# my-fullstack-app

A full-stack cleat application: a durable command path, a browser front-end, and
the plugins that sit between them — wired so the non-obvious settings are
already right.

Generated by `cleat init --template fullstack`.

## Run it

```sh
make up          # postgres + worker
make logs        # confirm the rate limiter mode -- see below
make deploy      # build the workflow to WASM and deploy it
open web/index.html
```

`make up` prints an API key on first start, when no keys exist yet. Export it as
`CLEAT_API_KEY` for `make run`.

## What is wired, and why

| Concern | Component | Note |
|---|---|---|
| Durable command path | `SubmitOrder` in `main.go` | started over HTTP, resumed after a crash |
| Duplicate suppression | `Idempotency-Key` header | a retried request returns the original run |
| Per-tenant rate limiting | `rate-limiter`, **`db` mode** | set in `plugin-config.json`; the default is weaker |
| Front-end | `web/index.html` | no framework, deliberately — see below |

## Check the rate limiter actually took

This is the one setting most likely to be wrong in a way nothing tells you
about.

`rate-limiter` has two modes. The default, `memory`, keeps token buckets in each
worker's process — so with N workers a tenant gets **N times** the configured
rate, and there is no cluster-wide ceiling at all. `db` mode coordinates through
a `rate_counter` table and holds across every worker.

`plugin-config.json` sets `db`. But if the plugin cannot reach a database it
**warns and falls back to `memory`, then starts normally**. A worker that
downgraded looks exactly like one that did not, unless you read the log:

```sh
make logs | grep rate-limiter
```

You want `mode=db`. If you see `falling back to memory mode`, the limit you
think you configured is not the limit you have.

Two further properties worth knowing before you rely on it as a spend control:
it **fails open** if the database errors — the right default for availability
and the wrong one for billing — and the read-then-increment is not one atomic
statement, so concurrent workers can overshoot slightly at a window boundary.
It is a cluster-wide *limiter*, not a cluster-wide *semaphore*.

## Why the browser does not wait

`SubmitOrder` is a durable run, not a request handler. It may take seconds or
days, it survives a worker dying, and it resumes where it stopped rather than
restarting. None of that fits inside an HTTP response.

So the shape is: **POST to start, then poll published state.** The workflow
calls `SetQueryState`, and the browser reads it back from
`GET /api/workflows/{id}/state?key=status` for one key, or
`GET /api/workflows/{id}/state` with no `key` at all to list everything the
run has published so far.

That read path is intentionally *not* a durable run. Serving reads by starting
workflows would write event history on every page refresh.

## Authentication, and the mistake to avoid

The API key the worker prints identifies the **whole tenant**. It must never
reach a browser.

`web/index.html` calls the API without one, which works only against a worker
started with `--require-auth=false` or through your own backend. For a real
application, use the `oauth-provider` plugin for per-user login and have your
own endpoint call cleat server-side with the tenant key.

Note the boundary: cleat's row-level security scopes by **tenant**. A user
principal exists at the HTTP layer (`SessionInfo` carries the email), but the
database does not know about it — so per-user authorisation inside a tenant is
your application's job, and the database will not catch a mistake there the way
it catches a cross-tenant one.

## Why there is no framework

The cleat playbooks say your front-end framework *stays rope*: unchanged,
unowned, not reimplemented. A scaffold that picked React or Svelte would
contradict that, and would put an npm toolchain inside a Go project.

`web/index.html` is a single file with no build step. Its job is to show the
**API contract** — start a run, poll state — not to be your application.
Replace it entirely. In production, serve your bundle from a CDN; cleat is the
origin and the API, not your bundler.

## A note on `plugin-config.json`

The worker passes this file's contents to **every** plugin, which each parse the
keys they recognise. There is no per-plugin section, so `{"mode": "db"}` reaches
all of them and only `rate-limiter` acts on it. Keep that in mind if you add a
plugin that wants a key of the same name.
