AI agent platform

Each run is a durable workflow: it calls a model, spends from a per-run budget, and can park until a human approves what it is about to do. The model it calls is the model-stub service in this example's compose file; in a deployment it is your provider.

What to look for

An approval is an event, not a call into the run. The workflow waits with event-triggers' await_event, and an event is matched by (tenant, event_type) — there is no addressing by run id anywhere in that path. So this page refuses to publish unless the run you selected is the one currently waiting; a second run parked on the same tenant could otherwise take the decision. The run_id this backend puts in the event is an audit trail, not an address.

The wait is about 30 seconds. The workflow polls 15 times two seconds apart (MaxApprovalPolls × ApprovalPollMs in agent.go) and then gives up on its own, reporting approval_timeout — a run that nobody answered is not an error, it is a decision the system made. Approving takes effect on the run's next poll, so up to two seconds of this page showing awaiting_approval after you press the button is expected.

A denial is not a failure. approved: false is handed back to the model as the tool's result and the run carries on, ending done — which is why the status after a denial reads approval_received and never approval_denied. AgentOutput's field comment in agent.go lists that fourth word; nothing writes it.

The compose file's model stub never asks for approval. It always calls save_report, so a run started from this page reaches done without parking and the buttons below never appear. Parking is what a real model's request_approval call produces — agent_test.go drives that branch, and agent.go is where the wait lives.
