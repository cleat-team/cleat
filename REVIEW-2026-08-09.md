## Verdict

The engineering core is stronger than the median project of this description. The durability
model is real, the CI signal is unusually trustworthy, and the project's self-documentation
(`tiers.yaml`, `CLAUDE.md`, `.golangci.yml`) is genuinely disciplined — `.golangci.yml` in
particular is the best-maintained file in the repo for the "no number without a re-deriving
command" rule.

But there are **six defects that would break a real deployment today** (B2–B7; B1 was
downgraded to medium during implementation — see the correction in its entry), and they
cluster in one place: **the gap between what CI exercises and what ships.** That is not
diffuse immaturity; it is a specific, fixable structural problem with a specific, fixable
cause.

This is assessed as an engineering artifact, not a product: there is no intent to compete
commercially with Temporal or DBOS, so gaps that are purely the absence of a commercial
offering are recorded and set aside rather than treated as backlog. What remains in scope is
correctness, coherence, and whether a claim the repo makes is true.

## What is genuinely strong

These held up to checking and should not be disturbed by the remediation work.

- **Fencing on terminal writes is correct.** `CompleteWorkflow`, `FailWorkflow`,
  `ContinueAsNew` and `FinalizeWorkflowSegment` all gate on
  `WHERE id=? AND assigned_to=? AND generation=?` and return `ErrFenceLost` rather than
  silently no-opping (`engine/store_lifecycle.go:224`). `ContinueAsNew` is atomic — events,
  new run and old-run completion in one transaction.
- **Determinism fencing is real, not documentation-only.** `Now()` derives from the last
  consumed event's timestamp during replay; `Random()` is `sha256(workflowID:step:seq)`.
  Both are registered identically on wasmtime and wazero through one shared
  `registerAllImports`, so the "registered in one options struct but not another" defect
  class does not reproduce for these primitives.
- **Build-time determinism analysis for Go is real static analysis** — `internal/closure`
  uses `go/types` for map-type detection, not string matching — and it is on by default in
  `cleat build`, which is the correct layer for it.
- **The CI signal is worth something.** Measured this review: **6094 tests, 0 failures,
  5 skips** across 21 packages. Dialect coverage was proven by subtest symmetry — exactly
  160 `postgres` / 160 `mysql` / 160 `mssql` subtests, zero "not set" skips — which is the
  `CLAUDE.md`-mandated "assert the connection, do not infer it from `ok`" check satisfied
  directly rather than by wall-clock inference. CI digest-pins all three DB images, uses
  `pipefail` on every DB-dependent job, carries exactly one `continue-on-error` (the
  explicitly non-required coverage job), and tests the GitHub merge commit rather than the
  raw branch head.
- **The "failure wearing a skip's clothing" hunt largely succeeded.** `grep` over every
  `t.Skipf` message for `crash|compat|not support|todo|broken|flak` returns **zero hits**.
- **`plugin.Secret` is a properly designed fix**, not a convention. It redacts through
  `MarshalJSON`, `String()` **and** `fmt.Formatter` (covering `%v`/`%+v`/`%#v`, not just
  JSON), `Reveal()` is a method so real uses are greppable, and `UnmarshalJSON` refuses the
  redacted placeholder so a write-back cannot clobber a stored secret. Backed by an
  AST-based guard test that generalizes to new plugins.
- **Real judgment in the write path**: write-ahead call intent so a crash mid-call is
  detectable on replay, auto-`ContinueAsNew` at an event cap, cancellation polled before
  each fresh call with a documented fail-open rationale.
- **`set_config(..., true)`** is used consistently — transaction-local, correct under
  connection pooling — and `assert_tenant_set()` makes the RLS fence fail closed.
- **Migrations are transactional per-file** with a real version table and Postgres
  advisory-lock serialization for concurrent worker-boot races.

## Ship-blockers

### B1 — MySQL schema drift: `NOT NULL` where the engine writes `NULL`

> **CORRECTION, 2026-08-09, during implementation.** This finding was first written as
> "saga compensation and child workflows are **broken** on MySQL", rated a ship-blocker. That
> was **wrong on severity**, and the error is instructive enough to keep rather than quietly
> replace.
>
> The original proof used a bare `INSERT`. **Production uses `INSERT IGNORE`**
> (`engine/mysql_events.go:54`, `engine/mysql_store.go:347`), and MySQL downgrades
> `ER_BAD_NULL_ERROR` under `IGNORE` to a *warning*, inserting the implicit default `''`.
> Measured:
> ```
> INSERT IGNORE INTO t VALUES ('wf-1', 0, NULL, NULL);
> Warning 1048 Column 'service' cannot be null
> Warning 1048 Column 'request' cannot be null
> → row present, service='', request=''
> ```
> Since `''` is exactly the Go value that produced the `NULL`, it **round-trips correctly**
> and the checksum chain still matches. Sagas and child workflows are *not* broken on MySQL.
>
> This is the same mistake the review criticises elsewhere: I tested a layer adjacent to the
> one that runs in production. What survives is below, and it is real but narrower.

**What is actually true (PROVEN):**

1. **The schema drift is real.** `migrations/mysql/001_schema.sql:116-118` declares
   `event_history.service`, `.operation` and `.request` as `NOT NULL`; Postgres and MSSQL
   leave the equivalents nullable. The engine writes all three through `nullStr()`
   (`engine/store_events.go:141`), which converts `""` to SQL `NULL`, and `DurableDefer`
   (`engine/durablecalls.go:400`), child-workflow events (`engine/children.go:209`),
   `EventTypeAwaitSignals` and `EventTypeUpdateHandler` all leave them unset.
2. **One MySQL path would genuinely fail**, because it does *not* use `INSERT IGNORE`:
   `MySQLStore.WriteCallIntent` (`engine/store_intent.go:130-143`) is a plain `INSERT` passing
   `nullStr(rec.Service)`, `nullStr(rec.Op)`, `nullStr(rec.Request)`. Service and operation are
   non-empty for any durable call (validated by `validServiceName`), but **`Request` is not
   validated non-empty anywhere** — `grep 'requestJSON == ""' engine/durablecalls.go engine/memory.go`
   returns nothing. A write-ahead-intent operation invoked with an empty request body errors
   with `ER_BAD_NULL_ERROR` on MySQL and succeeds on the other two dialects. This is opt-in
   (`WithWriteAheadIntentOps`), which is why nobody has hit it.
3. **`INSERT IGNORE` is masking more than this.** It suppresses *every* error class on that
   statement — duplicate key, data truncation, out-of-range — not just the NULL coercion. The
   dialect drift is invisible today specifically because the main write path cannot report a
   constraint problem at all.
4. **No test can see any of it**, which is the durable lesson: `engine/testutil/mysql_schema.go:91-93`
   builds those columns **nullable**, so every MySQL test runs against a schema production
   never uses. The live WS-3 test database reports `service … YES`.
   `migration/mysql_bootstrap_test.go` proves the migrations *apply*; nothing proves the engine
   *works against what they produce*. That gap is what Stream A exists to close, and it stands
   regardless of this correction.

**Revised severity: medium.** One narrow genuinely-failing path, plus silent dialect drift
masked by a blanket error suppressor. Not a ship-blocker. The remediation is unchanged — align
the MySQL schema with the other two dialects, and build test databases from the shipped
migrations — but the justification is "dialect parity and test fidelity", not "sagas are
broken."

### B4 — Per-step event writes carry no fencing token

**PROVEN (mechanism); SUSPECTED (live exploitability under concurrent load — not run).**

`grep 'generation\|assigned_to' engine/flush.go engine/adaptive_flush.go engine/store_intent.go`
returns **nothing**. Terminal and segment-boundary writes are fenced; the per-step flush path
and the write-ahead-intent path are not. A worker that stalls, is reaped (generation bumped,
`assigned_to` cleared, workflow reclaimed), then resumes, can durably write or overwrite
`event_history` rows interleaved with its successor's — via the
`ON CONFLICT (workflow_id, step) DO UPDATE` clause at `engine/flush.go:66`.

Compounding: the per-workflow generation-checked `Heartbeat` (`engine/db.go:236`) that could
cut off a specific zombie mid-flight is **never called in production** —
`cmd/cleat-worker/setup.go:1980` calls only `BatchHeartbeat`, which by its own doc comment
"intentionally does NOT check per-workflow generation."

The eventual `FinalizeWorkflowSegment` from the zombie will fail its fence check, but any
event rows it flushed and any live side effects it dispatched before then are permanent.

## Serious, below the blocker line

### S1 — Six tenant-scoped tables have no RLS

**PROVEN (live query + migration read).** `migrations/postgres/001_schema.sql:479-554` enables
and FORCEs RLS on eight tables. Live `pg_class` query confirms those eight — and confirms six
tables carrying a `tenant_id` column with `relrowsecurity = f`:

`concurrency_keys`, `idempotency_keys`, `workflow_update_requests`, `kv_store`,
`feature_flags`, `tenant_api_keys`.

Same gap on MSSQL, plus a parity gap: MSSQL's `CREATE SECURITY POLICY` block omits
`dbo.workflow_promises`, which Postgres does protect.

Mitigating: Go-level `WHERE tenant_id = ?` filtering is applied consistently for the tables
checked — **except** three `idempotency_keys` UPDATEs (`engine/store_lifecycle.go:361,418,526`)
which filter by `workflow_id` only. So today this is "no database backstop, and one missed
`WHERE` clause is a silent cross-tenant leak," which directly contradicts `tiers.yaml`'s claim
that isolation is database-enforced.

### S2 — No retention for completed workflows

**PROVEN.** `retentionLoop` (`cmd/cleat-worker/setup.go:2375`) calls `DeleteExpiredEvents`,
which deletes `event_history` rows only. `DeleteDeadLetteredWorkflows` (`engine/db.go:1101`)
covers dead-lettered instances only. Nothing ever purges a **completed**
`workflow_instances` row — repo-wide grep for a production `DELETE FROM workflow_instances`
outside those two paths returns nothing.

Compounding: `ListWorkflows` (`engine/db.go:304`) builds `ILIKE` filters against
`input`/`result`/`error_msg`/`def_name` with no supporting index (the one GIN index on
`input` supports JSONB containment, not `LIKE`). Dashboard list latency therefore degrades
with **lifetime** workflow count, not active count, with no admin lever to reclaim it.

### S3 — Postgres tenant deletion does not delete tenant data

**PROVEN.** `admin.drop_tenant` (`migrations/postgres/001_schema.sql:144-158`) drops the
tenant's plugin schema and role and two bookkeeping rows. It does not touch
`workflow_instances`, `event_history`, `workflow_signals`, `workflow_schedules`,
`workflow_tags`, `workflow_routing`, `workflow_promises`, `workflow_update_requests`,
`concurrency_keys` or `admin.tenant_api_keys` — the tables most likely to carry PII.

It also has **no Go caller anywhere**. MySQL is fine here (`DropTenantDatabase` drops the
per-tenant database); MSSQL has no deletion mechanism at all.

Consequence: a GDPR/CCPA erasure request against the primary documented backend cannot be
honored by anything that ships, and the failure is silent.

### S4 — Replay loses the non-retryable-error classification, two independent ways

**PROVEN.**
- **Compaction.** `CompactedEvent` (`engine/compaction.go:154`) has no `ErrNonRetryable`
  field; `grep -c ErrNonRetryable engine/compaction.go engine/compaction_test.go` returns
  0 and 0. Past `DefaultCompactionThreshold` (1000 events), a call originally classified
  non-retryable replays as retryable — engine-introduced non-determinism, guest-visible.
- **Heartbeat path.** `freshCallWithHeartbeat` records `ErrNonRetryable`
  (`engine/heartbeats.go:124`) but `replayCallWithHeartbeat` ignores it and unconditionally
  returns the retryable code (`:205-209`). The comment there is stale — it says the class
  "was never persisted", which line 124 makes false. The replay test fixture at
  `heartbeats_test.go:169` leaves `ErrNonRetryable` unset, so it cannot catch this.

This is §2.35's divergence bug reintroduced on the one path the original fix did not touch.

### S5 — MSSQL `event_history.request` is `NVARCHAR(255)`

**PROVEN (schema asymmetry); SUSPECTED (truncate vs reject behaviour — not run).**
`migrations/mssql/001_schema.sql:226` declares `request NVARCHAR(255)` while the sibling
`response` is `NVARCHAR(MAX)` and both Postgres and MySQL use unbounded text.
`engine/mssql_events.go:490` writes base64 into it, so payloads over ~190 bytes overflow.
Because the event checksum is computed in Go over the untruncated value, silent truncation
would make integrity verification report false corruption on reload.

### S6 — Two plugins are unreachable under the secure default

**PROVEN.** `plugins/webhookingest/routes.go:28` registers `POST /ingest/{source_id}` (an
external webhook receiver with its own HMAC verification) and
`plugins/oauthprovider/routes.go:74` registers `GET /oauth/{provider}/callback` (a
third-party IdP redirect target) on the same mux that `auth.Middleware` wraps. Only
`/healthz` and `/metrics` are exempt, and no exemption mechanism exists. Under the default
`--require-auth=true`, GitHub/Stripe hitting `/ingest/...` and a browser following an OAuth
redirect both get 401 before the plugin's own verification runs.

Either these plugins have never worked end to end under the secure default, or operators are
being pushed toward `--require-auth=false`, which `tiers.yaml` declares unsupported.

### S7 — A live subsystem has zero tests; two dead files have no guard

### S8 — `plugins/scheduledbackup` claims capabilities it does not have

**PROVEN.** Its own doc comments claim "manual backup/restore via HTTP API and CLI"
(`plugin.go:2`, `cron.go:2`) and "Scheduled PostgreSQL backups to **S3**" (`plugin.go:22,54`).
`grep -rin restore plugins/scheduledbackup/*.go` finds no implementation; `s3_bucket`/`s3_prefix`

is not `plugin.Secret`, is not in the secret-field guard's allowlist (its pattern vocabulary
has no `dsn`/`connection_string` entry), and is passed as a literal `exec.CommandContext`
argument — visible in `ps`/`/proc/*/cmdline` to any co-resident user.

### S12 — The only published tag declares the wrong module path

**PROVEN, 2026-08-09, during implementation. Upgraded from SUSPECTED, and worse than the
original suspicion.** Found by Stream F while checking the onboarding path; confirmed directly:

```
$ head -1 go.mod                    → module github.com/cleat-team/cleat
$ git show v0.1.0:go.mod | head -1  → module github.com/rcownie/cleat
$ git show v0.1.0:go.mod | grep -A3 '^replace'
                                    → replace github.com/rcownie/cleat/cleat => ./cleat
```

`v0.1.0` is the **only** tag in the repository, and it declares its module path as
`github.com/rcownie/cleat` — the pre-rename identity. So
`go install github.com/cleat-team/cleat/cmd/cleat@latest` resolves to a module whose declared
path does not match the one requested, and fails.

**That command is line 12 of `README.md` and the first step of every onboarding document.**
It has never worked for anyone outside a local checkout of this repository.

**A retag alone does NOT fix this.** Investigated 2026-08-09 against the real proxy and a
local file-based proxy. Three findings, each verified by running it:

1. **Confirmed live.** `go get github.com/cleat-team/cleat@v0.1.0` against
   `proxy.golang.org` returns exactly:
   `module declares its path as: github.com/rcownie/cleat / but was required as:
   github.com/cleat-team/cleat`. That version is now immutably cached, so `v0.1.0` cannot be
   reused — the next tag must be a new version.

2. **The three first-party modules form a dependency cycle**, and both directions are real:
   `cmd/cleat` (the binary people `go install`) imports `github.com/cleat-team/cleat/cleat`
   and `cleat/localdev`; `cleat/` imports `github.com/cleat-team/cleat/engine`.
   Re-derive: `go list -deps -f '{{.ImportPath}}' ./... | grep cleat-team/cleat/cleat`.
   All three `go.mod` files require the other at the **unresolvable version `v0.0.0`**, made
   to work locally only by `replace` directives.

3. **`go install <pkg>@<version>` refuses any module whose `go.mod` contains a `replace`
   directive** — a stricter rule than ordinary dependency resolution, which merely ignores
   them. Measured:
   ```
   go install github.com/cleat-team/cleat/cmd/cleat@v0.2.0
   → The go.mod file for the module providing named packages contains one or more
     replace directives. It must not contain directives that would cause it to be
     interpreted differently than if it were the main module.
   ```
   So **the README's line-12 install command could never have worked**, whatever the tags
   said, as long as those `replace` directives are present.

4. **A `go.work` workspace does not substitute for them.** Tested: with the replaces removed
   and `use (. ./cleat ./cleat/backendkit)` in place, local builds still fail, because Go
   resolves the required *version's* `go.mod` for the module graph regardless of the
   workspace. Only `replace` made local development work.

**What does work, verified end to end:** with real published versions on both sides, the
cycle resolves and an external consumer compiles. Proven by building a local file-based
`GOPROXY` containing hand-packaged `v0.2.0` zips of both modules, then in a scratch module
running `go mod tidy` + `go build` on a program importing `github.com/cleat-team/cleat/cleat`
— it compiled.

**So there are two viable fixes, and it is a design decision, not a release chore:**

* **A — bootstrap the cycle.** Remove every first-party `replace`, set the requires to the
  version about to be tagged, then push the commit and *both* tags (`vX.Y.Z` and
  `cleat/vX.Y.Z`, plus `cleat/backendkit/vX.Y.Z`) together. Cheap. The cost is a window
  between pushing the commit and pushing the tags in which nothing builds — including CI —
  and local development permanently depends on the tags existing on the remote.
* **B — break the cycle.** Make `cmd/cleat` not import `cleat/` (it needs the scaffolding
  templates and `localdev`), or fold `cleat/` into the root module. Then the dependency is
  one-way, no bootstrap is needed, and `replace` can go away without a workspace. More work,
  and it is the answer that stops this recurring.

Deliberately not executed. Publishing a tag is irreversible — the proxy caches immutably, as
`v0.1.0` demonstrates — and choosing between A and B is the owner's call.

## Technical positioning: Temporal and DBOS

**Framing.** This is not a go-to-market analysis. There is no intent to compete commercially
with DBOS or Temporal, and the maturity and organization to do so are not present. The
comparison is kept for two narrower purposes: (a) to identify which design bets are actually
distinctive and therefore worth protecting from regression, and (b) to calibrate which gaps
are real engineering debt versus which are simply the absence of a commercial product.

That distinction changes the priority order. **Deprioritized as not-applicable:** no managed
cloud, no community or ecosystem, effort-to-first-success versus DBOS, ecosystem breadth,
"who is the buyer". **Still fully in scope**, because they are correctness or coherence
problems regardless of commercial intent: the replay-guarantee holes (S4), the dialect claim
versus the shipped CLI (B6 — solvable by narrowing the claim rather than building the
feature), retention and unbounded table growth (S2), and documentation that will cost future
sessions to re-derive.



### What is genuinely differentiated

**The core claim is a stronger replay guarantee, enforced by construction rather than by
developer discipline.** This is the differentiator, and it is a better one than the "no new
infrastructure" pitch, which DBOS matches.

Temporal and DBOS both make determinism a *convention*. A Temporal workflow can call
`time.Now()` or open a socket; nothing prevents it, and the failure surfaces later as a
replay divergence — or does not surface at all. DBOS's checkpoint model is usually described
as a lighter contract, and it is, but lighter means **weaker**: only step boundaries are
logged, so non-deterministic code *between* steps that changes which steps get called will
diverge on recovery with nothing to detect it. The developer is trusted not to write it.

Cleat closes this three ways that compose:

1. **The sandbox removes the ambient capability.** A WASM guest has no clock, no network, no
   filesystem and no OS entropy except through host functions that are recorded. This is the
   part neither competitor can retrofit: it is not a lint, it is the absence of the syscall.
2. **Host-side substitution makes the remaining sources replay-exact.** `Now()` derives from
   the last consumed event's timestamp; `Random()` is `sha256(workflowID:step:seq)`. So the
   two sources a guest legitimately needs are deterministic by construction, not by rule.
3. **Static analysis catches what is left** — the intra-guest sources the sandbox cannot see,
   principally map-iteration order — at *build* time, using real `go/types` analysis, before
   deploy. Temporal's equivalent signal arrives at runtime, on replay, in production.

(1) is what makes (3) tractable: static analysis alone is defeated by aliasing and dynamic
dispatch, which is why lint-based determinism checking is unsatisfying elsewhere. When the
capability is absent from the sandbox, the analyzer only has to cover the narrow residue.

**The second differentiator is operational, and it is underrated:** N versions of workflow
code running on **one** stateless worker pool. Temporal's Worker Versioning (GA 2026-03-30)
requires distinct worker *deployments* per version and traffic ramping between them. DBOS
pins in-flight workflows to the app version that started them — which, in a library model,
means keeping the old *application deployment* alive to serve them. Cleat's workflow code is
data, so an in-flight instance replays against its exact original bytes on whatever worker
picks it up. Nothing to route, no fleet to keep warm, no version-aware task queues. For a
team already reluctant to add infrastructure, "old versions drain themselves" is a larger
practical saving than the initial install difference.

Also genuinely uncommon: `cleat.NewSaga()`'s `AddParallel` with automatic LIFO compensation
across concurrent branches.

### Where that claim is currently undermined — by cleat, not by competitors

The differentiator is real, but three findings above are holes **in the flagship guarantee**,
which is why they matter more than their apparent severity:

- **S4 is engine-introduced non-determinism.** Compaction silently drops the
  non-retryable-error bit, and the heartbeat replay path ignores it. A workflow told "this
  failure is permanent" on first execution is told "retryable" on replay. That is precisely
  the class of divergence the whole architecture exists to make impossible, produced by the
  engine itself. **Fix this before publishing the replay-guarantee claim.**
- **The guarantee is Go-only today.** `cmd/cleat/vet_rust.go` and `vet_java.go` are
  substring matching over raw source, defeated by aliasing and false-positive on comments —
  and neither is invoked by `build_rust.go`/`build_java.go`, only by the separate `cleat vet`
  subcommand. Python's build path runs no determinism check at all. Only Go gets pillar (3).
- **wazero weakens pillar (1) — but only partly, and the distinction matters.** wazero cannot
  fence a *compute-bound* guest, which is a liveness and resource problem, not a determinism
  one: the capability boundary itself (no clock, no network except via recorded host calls)
  holds on both backends. Still, the silent fallback on *any* wasmtime init error (S10) means
  an operator can lose runaway-guest protection without noticing.

### The positioning problem is DBOS, not Temporal — but it is narrower than it looks

DBOS makes a nearly identical "your existing Postgres is the backend, no new infrastructure"
pitch, with no build step, native stack traces, four SDKs, a managed cloud, and a built-in
saga decorator. It also inherits the same single-Postgres scaling ceiling, so that axis does
not separate them.

What separates them is exactly the above: **cleat trades a build step for a guarantee.** That
is a defensible trade, and it is the one the marketing should lead with — not "no new
infrastructure", where DBOS is at parity and has a smoother on-ramp. The buyer is a team for
whom silent recovery divergence is expensive: payments, ledgers, provisioning, anything where
"it replayed differently and nobody noticed" is the nightmare rather than an inconvenience.

Two corrections to `DX_COMPARISON.md`, which currently argues the weaker case:
- Line 210's headline claim that **"no competitor has built-in Saga" is wrong for DBOS** —
  `@DBOS.workflow(saga=True)` runs compensations in reverse order automatically. It is
  accurate for Temporal, whose saga is sample code, not an importable primitive.
- Line 229 overstates Restate's infrastructure: it is a single binary with embedded RocksDB;
  Kafka is optional, not required. Lines 85 and 358 also contradict each other on whether
  per-call timeouts are done.

### Gaps that are real engineering debt

These are worth fixing whether or not anyone else ever uses this:

1. **No retention or archival** — unbounded table growth, and list latency that degrades with
   lifetime rather than active workflow count (**S2**). This one bites the author first.
2. **No indexed visibility.** `WorkflowFilter` is `LIKE` predicates on unindexed columns
   (`engine/store_types.go:137`). Fine at hundreds of workflows; the failure mode is gradual.
3. **`RegisterQueryHandler` is a half-wired API.** `engine/lifecycle.go:313` appends the
   handler *name* to a slice and nothing ever calls back into it — no host import, no HTTP
   route. It looks like Temporal's `QueryWorkflow`, so it will be assumed to work. Either
   wire it or delete it, per the `isReplaying()` precedent (#448), which handled exactly this
   shape correctly.
4. **Non-Go SDKs trail**, and cross-language replay coverage is Go↔Rust only — nothing
   verifies a Java or AssemblyScript guest replays a history the Go host recorded. This is a
   direct hole in the flagship guarantee, not a product gap.
5. **No performance numbers exist.** `benchmarks/comparative/results/template.md` is 100%
   placeholder tokens. The design doc's own estimate is ~312–1,562 claims/sec, with the claim
   path ~1/8 of the INSERT ceiling. Not urgent commercially — but it means nobody, including
   the author, knows where this actually falls over. Dated claim-latency numbers do exist
   (`docs/benchmarks/throughput.md`, 2026-05-15, with hardware).
6. **Stringly-typed routing.** `h.DurableCall("payments", "Charge", jsonString)` gives up
   compile-time safety. `cleat-gen` mitigates it; the default path does not.

### Gaps that are simply the absence of a commercial product — not debt

Recorded so they are not mistaken for backlog: no managed cloud; no community or ecosystem;
no case studies; multi-tenancy being 2-of-3 dialects (an explicit, measured product decision
— MySQL RLS emulation cost 6.1× on scans); and effort-to-first-success trailing
`temporal server start-dev`. None of these should consume a session.

**One caveat on that last point.** `cleat dev start` failing (**B7**) is not a market problem
— it is the first command in the README failing for *anyone*, including the author after a
long enough gap. Keep it in scope; the fix is minutes.
