# Third-Party Plugin Authoring Guide

This guide shows you how to build a third-party plugin for cleat. Third-party
plugins are WASM binaries that run inside the cleat worker. They let you extend
cleat with custom host functions that workflows can call, all without modifying
the cleat worker binary or the cleat codebase.

## 1. Overview: What a cleat plugin is

A cleat plugin exposes **host functions** -- typed, workflow-callable methods
that run inside the cleat worker process. Plugins are distributed as WASM
binaries (compiled from Go, Rust, Zig, or any language targeting `wasip1`).

### Distribution model

Third-party plugins are distributed through a **plugin index** (a Git repository
with an `index.yaml` file). Operators install plugins with:

```
cleat plugin install example/hello-world@^0.1.0
```

The CLI fetches the WASM binary, verifies its checksum, and stores it in the
local `plugin_defs` database table. The worker loads and instantiates the WASM
module at runtime when a workflow invokes one of its host functions.

### WASM sandbox

Plugins run inside a **wazero** sandbox with no access to:

- The filesystem (no WASI filesystem access)
- Network connections (no WASI sockets)
- Direct syscalls of any kind
- The host process memory

The only way a plugin interacts with the outside world is through **cleat host
function imports** -- a stable ABI that the cleat project maintains across releases.

### What you need

- A language that compiles to WASI preview 1 (`wasip1`) -- Go 1.21+ is the
  most tested path
- The `plugin.json` manifest describing your plugin's host functions and
  capabilities
- A host function ABI shim (provided as a Go library or generated by
  `cleat-gen-plugin`)

## 2. Quick start: minimal plugin

Here is the smallest possible plugin with a single host function.

### Step 1: Create the project

```
mkdir cleat-hello-world && cd cleat-hello-world
go mod init github.com/example/cleat-hello-world
```

### Step 2: Write plugin.json

```json
{
  "name": "example/hello-world",
  "version": "0.1.0",
  "description": "A minimal example third-party plugin",
  "author": "example-corp",
  "repository": "https://github.com/example/cleat-hello-world",
  "capabilities": {
    "database": false,
    "start_workflow": false,
    "signal_workflow": false
  },
  "host_functions": {
    "greet": {
      "description": "Returns a greeting for the given name",
      "input": {
        "type": "object",
        "fields": {
          "name": { "type": "string", "description": "Name to greet" }
        }
      },
      "output": {
        "type": "object",
        "fields": {
          "message": { "type": "string", "description": "The greeting message" }
        }
      },
      "idempotent": true
    }
  }
}
```

### Step 3: Write main.go

```go
package main

import (
    "encoding/json"
    "fmt"
)

// greetInput matches the input type in plugin.json.
type greetInput struct {
    Name string `json:"name"`
}

// greetOutput matches the output type in plugin.json.
type greetOutput struct {
    Message string `json:"message"`
}

// cleat_abi_version is the ABI version this plugin targets.
//
//export cleat_abi_version
func cleat_abi_version() int32 {
    return 1
}

// _start is the WASM entry point. It runs once when the module is instantiated.
//
//export _start
func _start() {
    fmt.Println("hello-world plugin loaded")
}

// greet is registered at plugin load time by the manifest. It receives
// a JSON string and returns a JSON string.
//
//export greet
func greet(ptr uint32, len uint32, outPtr uint32, outLen uint32) uint64 {
    // In a real implementation, read input from WASM linear memory,
    // call the business logic, and write output back.
    input := readString(ptr, len)

    var req greetInput
    if err := json.Unmarshal([]byte(input), &req); err != nil {
        return encodeError("invalid input: " + err.Error())
    }

    result := greetOutput{
        Message: fmt.Sprintf("Hello, %s!", req.Name),
    }
    out, _ := json.Marshal(result)

    writeString(outPtr, outLen, string(out))
    return encodeOK()
}

func main() {}
```

### Step 4: Build

```
GOOS=wasip1 GOARCH=wasm go build -o plugin.wasm .
```

### Step 5: Validate the manifest

```
cleat plugin validate --manifest plugin.json
```

### Step 6: Install locally for testing

```
cleat plugin install --manifest plugin.json --wasm plugin.wasm
```

## 3. Writing the manifest (plugin.json)

The manifest is the source of truth for your plugin. It describes the plugin's
identity, capabilities, and host function API.

### Required fields

```json
{
  "name": "example/hello-world",
  "version": "0.1.0",
  "description": "What your plugin does",
  "author": "your-org-or-name"
}
```

| Field | Description | Rules |
|-------|-------------|-------|
| `name` | Plugin identifier | `org/name` for community, `name` for official. Lowercase letters, digits, hyphens, underscores, forward slashes |
| `version` | Semantic version | Valid semver (e.g., `0.1.0`, `1.2.3`) |
| `description` | Short description | Displayed in `cleat plugin list` and in the index |
| `author` | Plugin author | Displayed in the security warning on install |

### Optional fields

```json
{
  "repository": "https://github.com/example/cleat-hello-world",
  "min_cleat_version": ">=1.0.0"
}
```

| Field | Description |
|-------|-------------|
| `repository` | URL to the plugin source code. Shown to operators during install so they can review the code. |
| `min_cleat_version` | Semver constraint for the minimum cleat version required. Plugins that use newer ABI features can set this to prevent installation on older workers. |

### Capabilities

```json
{
  "capabilities": {
    "database": false,
    "start_workflow": false,
    "signal_workflow": false,
    "http_routes": false,
    "http_middleware": false,
    "call_plugin": ["llm"],
    "background_worker": false
  }
}
```

| Capability | Default | Description |
|------------|---------|-------------|
| `database` | `false` | Access the tenant's PostgreSQL database. Grants `*sql.DB` in the environment. |
| `start_workflow` | `false` | Can start new workflows. Defaults to denied for community plugins. |
| `signal_workflow` | `false` | Can signal running workflows. Granted by default for community plugins. |
| `http_routes` | `false` | Can register HTTP routes. Denied by default for community plugins. |
| `http_middleware` | `false` | Can register HTTP middleware. Denied by default. |
| `call_plugin` | `[]` | List of plugins this plugin can call via `plugin_call`. An empty list denies all. `["*"]` allows all. |
| `background_worker` | `false` | Can run background goroutines. Denied by default. |

Be conservative: only declare capabilities you actually need. Each capability
is a vector for accidental damage if your plugin has a bug.

### Host functions

```json
{
  "host_functions": {
    "my_func": {
      "description": "What this function does",
      "input": { "type": "object", "fields": { ... } },
      "output": { "type": "object", "fields": { ... } },
      "idempotent": false,
      "streaming": false
    }
  }
}
```

| Field | Required | Description |
|-------|----------|-------------|
| `description` | Yes | Human-readable description. Displayed as JSDoc/Python docstring in generated SDK wrappers. |
| `input` | Yes | Type definition for function input. Can be a simple type, named type reference, or inline object. |
| `output` | Yes | Type definition for function output. Same rules as input. |
| `idempotent` | No (default: `false`) | If `true`, the engine re-invokes this function during replay instead of returning cached output. Use for read-only functions (lookups, queries). |
| `streaming` | No (default: `false`) | If `true`, the function returns a stream of events rather than a single response. |

### Types

Named types let you share type definitions across multiple host functions:

```json
{
  "types": {
    "UserInfo": {
      "type": "object",
      "fields": {
        "id": { "type": "string", "description": "User ID" },
        "name": { "type": "string", "description": "Display name" },
        "email": { "type": "string", "description": "Email address", "optional": true }
      }
    }
  },
  "host_functions": {
    "getUser": {
      "input": { "type": "object", "fields": { "userId": { "type": "string" } } },
      "output": { "type": "UserInfo" },
      "idempotent": true
    },
    "listUsers": {
      "input": {},
      "output": { "type": "object", "fields": { "users": { "type": "array", "items": { "type": "UserInfo" } } } },
      "idempotent": true
    }
  }
}
```

### Supported types

| Type | JSON representation | Go type | TypeScript type | Python type |
|------|---------------------|---------|-----------------|-------------|
| `string` | JSON string | `string` | `string` | `str` |
| `int64` | JSON number | `int64` | `number` | `int` |
| `float64` | JSON number | `float64` | `number` | `float` |
| `bool` | JSON boolean | `bool` | `boolean` | `bool` |
| `bytes` | Base64-encoded string | `[]byte` | `Uint8Array` | `bytes` |
| `timestamp` | RFC 3339 string | `string` | `string` | `str` |
| `uuid` | UUID string | `string` | `string` | `str` |
| `object` | JSON object | `struct` | `interface` | `@dataclass` |
| `array<T>` | JSON array | `[]T` | `T[]` | `list[T]` |
| `map<K,V>` | JSON object | `map[K]V` | `Record<K, V>` | `dict[K, V]` |

## 4. Implementing host functions

### The PluginFunc signature

Host functions follow this ABI:

```go
//export my_host_function
func myHostFunction(inputPtr uint32, inputLen uint32, outputPtr uint32, outputMax uint32) uint64
```

Parameters:
- `inputPtr`, `inputLen`: pointer and length of the JSON input string in WASM
  linear memory
- `outputPtr`, `outputMax`: pointer and maximum length of the output buffer in
  WASM linear memory

Return value: a packed `uint64` where:
- Lower 32 bits: error code (0 = success, non-zero = error)
- Upper 32 bits: actual length of output written

### CallContext

When a workflow calls your host function, the engine injects context via the
`cleat_get_call_context` import. Your WASM module can call this import to
retrieve the tenant ID and workflow ID of the calling workflow:

```go
//go:wasmimport cleat cleat_get_call_context
func cleat_get_call_context(ptr uint32, maxLen uint32) uint64
```

The returned string is JSON:

```json
{
  "tenant_id": "a1b2c3d4-...",
  "workflow_id": "wf_abc123"
}
```

### Error handling

Return errors as JSON strings in the output buffer with a non-zero error code:

```go
func encodeError(msg string) uint64 {
    errJSON := `{"error":"` + msg + `"}`
    len := writeString(outPtr, outMax, errJSON)
    return (uint64(len) << 32) | 1
}
```

The engine records the error in `event_history` and surfaces it in the workflow
execution history.

### Idempotent vs. non-idempotent

- **Idempotent functions** (`idempotent: true`): The engine re-invokes these
  during replay instead of caching results. Use for pure lookups, queries, and
  other side-effect-free operations.
- **Non-idempotent functions** (`idempotent: false`, default): The engine
  records input/output in `event_history` and returns cached output during
  replay. Use for mutations, external API calls, and operations with side
  effects. Keep output small -- it is persisted in the database.

## 5. Building

### Go

```makefile
build:
    GOOS=wasip1 GOARCH=wasm go build -o plugin.wasm .

validate:
    cleat plugin validate --manifest plugin.json

all: validate build
```

Important Go build notes:
- Use `GOOS=wasip1` (not `GOOS=wasm`) -- this gives you WASI preview 1 APIs
- `GOARCH=wasm` selects the WebAssembly architecture
- Avoid CGO dependencies (CGO_ENABLED=0, which is the default for `wasip1`)
- Some Go standard library packages don't compile for WASM (e.g., `net` with
  raw sockets, `os/exec`). Test your build early.
- The resulting `.wasm` file is typically 2-5 MB for a simple plugin.

### Rust

```toml
# Cargo.toml
[package]
name = "my-plugin"
version = "0.1.0"
edition = "2021"

[lib]
crate-type = ["cdylib"]
```

```makefile
build:
    cargo build --target wasm32-wasip1 --release
    cp target/wasm32-wasip1/release/my_plugin.wasm plugin.wasm
```

### Validate before publishing

Always validate your manifest before publishing:

```
cleat plugin validate --manifest plugin.json
```

This checks:
- Required fields are present
- Plugin name follows naming conventions
- Semantic version is valid
- Host function names don't contain reserved characters
- Type references resolve correctly

## 6. Testing

### Local install test

Install your plugin locally to verify it works end-to-end:

```
cleat plugin install --manifest plugin.json --wasm plugin.wasm
```

This stores the plugin in the local `plugin_defs` table. You can then write a
workflow that calls your host function and run it with `cleat workflow run`.

### Table-driven unit tests

Write Go tests that exercise your host function logic directly (no WASM needed):

```go
func TestGreet(t *testing.T) {
    input := greetInput{Name: "World"}
    result := doGreet(input)
    if result.Message != "Hello, World!" {
        t.Errorf("expected 'Hello, World!', got %q", result.Message)
    }
}
```

### SDK compatibility test

Generate SDK wrappers for your plugin and verify they compile:

```
cleat plugin generate-sdk --manifest plugin.json --lang typescript --out ./generated/
```

Then check the generated types match what workflow authors expect.

## 7. Publishing

### Step 1: Create a GitHub release

1. Push your plugin code to a public GitHub repository
2. Tag the release: `git tag v0.1.0 && git push origin v0.1.0`
3. Create a GitHub Release from the tag
4. Upload `plugin.wasm` and `plugin.json` as release assets

### Step 2: Compute the checksum

```
sha256sum plugin.wasm
```

### Step 3: Submit a PR to the plugin index

1. Fork `github.com/cleat-team/cleat-plugins`
2. Add your plugin to `index.yaml`:

```yaml
plugins:
  - name: example/hello-world
    description: A minimal example third-party plugin
    author: example-corp
    repository: https://github.com/example/cleat-hello-world
    versions:
      - version: 0.1.0
        wasm_url: https://github.com/example/cleat-hello-world/releases/download/v0.1.0/plugin.wasm
        manifest_url: https://github.com/example/cleat-hello-world/releases/download/v0.1.0/plugin.json
        checksum: "sha256:abc123def456..."
        min_cleat_version: ">=1.0.0"
```

3. Open a Pull Request against the `cleat-plugins` repository
4. The CI pipeline validates:
   - `plugin.json` passes JSON Schema validation
   - Checksum matches the binary at `wasm_url`
   - Plugin name doesn't use the `cleat/` prefix (reserved for official plugins)
   - Plugin name doesn't collide with an existing entry
5. Once merged, operators can install your plugin with:
   ```
   cleat plugin install example/hello-world@^0.1.0
   ```

### Publishing checklist

- [ ] `manifest.json` passes `cleat plugin validate`
- [ ] WASM binary compiles without errors
- [ ] Plugin name follows naming conventions (`org/name`)
- [ ] Capabilities are set to the minimum needed (`database: false` if not needed)
- [ ] `repository` field points to the public source code
- [ ] `min_cleat_version` is set if the plugin uses recent ABI features
- [ ] Checksum is computed and recorded

## 8. Capability declaration guidance

### Be minimal

Only declare capabilities your plugin actually uses. Each capability widens the
blast radius if your plugin has a bug:

- If your plugin only does string manipulation, set `database: false`
- If your plugin only reads data, consider marking functions as `idempotent: true`
- If your plugin doesn't start workflows, set `start_workflow: false`
- If your plugin calls another plugin, list only the plugins it calls in
  `call_plugin` -- don't use `["*"]` unless it genuinely needs to call any
  plugin

### Capabilities that prompt warnings

Installing a community plugin with these capabilities prompts a highlighted
warning:

- **`start_workflow: true`** -- the plugin can create arbitrary workflows,
  potentially consuming resources
- **`http_routes: true`** -- the plugin can register HTTP endpoints that
  receive external requests
- **`http_middleware: true`** -- the plugin can intercept all HTTP requests
- **`background_worker: true`** -- the plugin runs persistent background
  goroutines
- **`call_plugin: ["*"]`** -- the plugin can call any other plugin's host
  functions

### Default operator limits

Operators configure default limits for community plugins in the worker config:

```json
{
  "plugin_capability_limits": {
    "database": true,
    "start_workflow": false,
    "signal_workflow": true,
    "http_routes": false,
    "http_middleware": false,
    "background_worker": false,
    "call_plugin": []
  }
}
```

A plugin whose manifest declares capabilities exceeding these limits is refused
at install time with a clear error message.

## 9. Naming conventions

### Official plugins (cleat project)

```
llm         → plugins.llm.chat(...)
blobstore   → plugins.blobstore.put(...)
kvstore     → plugins.kvstore.get(...)
```

Official plugins use bare names without an organization prefix. They ship with
the cleat-worker binary. Only the cleat project can publish plugins under bare
names.

### Third-party plugins

```
example/hello-world     → plugins["example/hello-world"].greet(...)
acme/salesforce         → plugins["acme/salesforce"].listCases(...)
mycorp/jira             → plugins["mycorp/jira"].getIssue(...)
```

Third-party plugins use an `org/name` format where `org` identifies the
publishing organization. This makes the trust boundary visible in workflow
code:

```typescript
// Clear from reading: one is official, one is third-party
const summary = await plugins.llm.chat({ ... });
const cases = await plugins["acme/salesforce"].listCases({ ... });
```

### Rules

- Plugin names are lowercase
- Use hyphens or underscores for multi-word names: `example/rate-limiter`,
  `mycorp/jira_sync`
- Maximum 64 characters
- The `cleat/` prefix is reserved for official cleat plugins
- Plugin names must match `^[a-z][a-z0-9_-]*(/[a-z][a-z0-9_-]*)?$`

## 10. Versioning

### Semver

Plugins MUST use semantic versioning (`MAJOR.MINOR.PATCH`):

- **MAJOR**: Breaking changes to host function signatures (input/output types,
  function renames, removals)
- **MINOR**: New host functions, new optional fields, new capabilities
- **PATCH**: Bug fixes, documentation changes, internal refactoring

### Deprecation

To deprecate a version, update the index entry:

```yaml
- version: 0.1.0
  deprecated: true
  deprecation_message: "Use 0.2.0 instead"
  wasm_url: ...
  checksum: "sha256:..."
```

The `cleat plugin install` command skips deprecated versions by default.

### Compatibility

- Plugins MUST maintain backward compatibility within a MAJOR version
- Adding new optional fields to existing host functions is a MINOR change
- Removing or renaming a host function requires a MAJOR bump
- Changing input/output types in a breaking way requires a MAJOR bump

### Checksum verification

Every version in the index includes a SHA-256 checksum of the WASM binary.
When an operator installs or updates a plugin, the CLI:

1. Downloads the WASM binary from `wasm_url`
2. Computes its SHA-256 hash
3. Verifies it matches the checksum in the index
4. Cross-checks against the checksum in the manifest (if available)

If checksums don't match, installation is refused.

## 11. Host function ABI reference

### WASM imports available to plugins

These imports are provided by the cleat worker at runtime. Your WASM module can
import and call them. They are stable across cleat releases (within the same
ABI version).

#### `cleat_plugin_call`

```
cleat_plugin_call(name_ptr, name_len, func_ptr, func_len, input_ptr, input_len, response_ptr, response_max) -> i64
```

Call a host function on a plugin. The name is the target plugin name, and
`func` is the host function name. Returns a packed i64 with error code in the
low 32 bits and response length in the high 32 bits.

```go
//go:wasmimport cleat cleat_plugin_call
func cleat_plugin_call(namePtr, nameLen, funcPtr, funcLen, inputPtr, inputLen, respPtr, respMax uint32) uint64
```

#### `cleat_plugin_call_streaming`

```
cleat_plugin_call_streaming(name_ptr, name_len, func_ptr, func_len, input_ptr, input_len, stream_id_ptr) -> i64
```

Start a streaming call to a plugin host function. Returns a stream ID (in the
high 32 bits) on success.

#### `cleat_read_stream`

```
cleat_read_stream(stream_id, buf_ptr, buf_max) -> i64
```

Read the next chunk from a stream. Returns the number of bytes written and
whether the stream is complete.

#### `cleat_close_stream`

```
cleat_close_stream(stream_id) -> i64
```

Close a stream. Cleanly terminates a streaming call.

#### `cleat_log`

```
cleat_log(level, msg_ptr, msg_len)
```

Log a message through the cleat logging system. Level is 0 (debug), 1 (info),
2 (warn), or 3 (error).

```go
//go:wasmimport cleat cleat_log
func cleat_log(level uint32, msgPtr, msgLen uint32)
```

#### `cleat_get_tenant_id`

```
cleat_get_tenant_id(buf_ptr, buf_max) -> i64
```

Get the tenant ID of the calling workflow. Writes the UUID string to the
buffer. Returns (length << 32) | error_code.

#### `cleat_get_call_context`

```
cleat_get_call_context(buf_ptr, buf_max) -> i64
```

Get the full call context (tenant ID and workflow ID) as JSON. Returns
(length << 32) | error_code.

### ABI versioning

Your WASM module exports `cleat_abi_version` to declare which ABI version it
targets:

```go
//export cleat_abi_version
func cleat_abi_version() int32 {
    return 1
}
```

The worker checks this version before loading:

| ABI version | Minimum cleat version | Notes |
|-------------|----------------------|-------|
| 1 | 1.0.0 | Initial stable ABI. All imports listed above are available. |

If a plugin requires a newer ABI than the worker supports, the worker refuses
to load it with a clear error message.

## 12. Limitations and known issues

### Go WASM limitations

- **No `net` package**: Go's HTTP client does not work in WASI preview 1. You
  cannot make outbound HTTP requests from a WASM plugin directly. Use the
  `cleat_plugin_call` import to call another plugin that handles networking.
- **No `os/exec`**: You cannot spawn subprocesses.
- **No CGO**: C dependencies don't compile.
- **No `syscall/js`**: That's for browser WASM, not WASI.
- **File size**: Go WASM binaries are 2-5 MB due to the Go runtime. Consider
  TinyGo for smaller binaries (though TinyGo has its own limitations).

### Performance

- WASM plugins have overhead compared to compile-time Go plugins. The first
  call to a WASM plugin function incurs wazero compilation time (~50-200ms).
  Subsequent calls use the compiled cache.
- For hot-path functions (called on every workflow step), consider whether a
  compile-time plugin (first-party) would be more appropriate.
- WASM plugins are subject to gas metering and memory limits. Very
  compute-intensive operations may be throttled.

### Isolation

- WASM plugins share the tenant schema with other plugins for the same tenant.
  Plugin A can read or corrupt Plugin B's data within the same tenant.
- There is no per-plugin schema isolation within a tenant. This is a known gap
  (see [plugin-security.md](plugin-security.md) for mitigations).

### Scope

- WASM plugins cannot register HTTP routes, HTTP middleware, or background
  workers in the current ABI. These capabilities are planned for future ABI
  versions.
- WASM plugins cannot directly access PostgreSQL -- they rely on the
  `cleat_plugin_call` import to invoke host functions on plugins that have
  database access. A WASM plugin that needs database access must call a plugin
  compiled into the worker (like `pgvector` or `blobstore`).

### Debugging

- WASM debugging tools are less mature than native Go debugging. Use
  `cleat_log` calls for debugging output.
- There is no step debugger for WASM modules inside wazero. Test thoroughly
  before publishing.
