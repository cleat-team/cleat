- **A Python or C# component execution can no longer abort the whole worker with `fatal error: invalid pointer found on stack` (cleat#4417).** Registering a component's host functions passed a callback-registry id, a small counter such as `0x215`, from C back into Go as an `unsafe.Pointer`. While that value sat in a pointer-typed stack slot, a stack copy by the Go runtime found a non-pointer where a pointer must be and killed the process, and with it every run on that worker. It was rare (two occurrences are known, one at each of the two registration sites, in 2 of the 105 Tier 1 gate runs whose logs were readable), it was on every component execution's path, and it was there from the first component support. The id now stays an integer in Go: a C function takes it as a `uintptr_t` and makes the call that consumes it itself, so no Go value of pointer type ever holds it. A test fails if a C helper in the package takes an integer and returns a `void *`, or if Go calls the C `add_func` directly. The crash is deterministic when the compiler is told to move the stack at every function prologue (`go test -gcflags='all=-d=maymorestack=runtime.mayMoreStackMove'` over a test that registers a component's host functions): it aborts before this change with the same `fatal error: invalid pointer found on stack` and passes after it. That command is not a test in the tree.
