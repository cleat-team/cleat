- **An update sent to a run that was suspended in a wait is handled when the run wakes, in every SDK (cleat#4511).** A run blocked in ONE long `AwaitSignals`, `AwaitPromise` or child await handled an update only if it was already pending when the run first reached the wait. An update that arrived after the run had suspended woke it, the replay reached the same wait and suspended again without polling, the update's promise stayed `pending`, and the next update of the same name was refused with `409 update_already_pending`. A run that waited in one-second slices was not affected, which is why the shipped fixture did not show it. The poll in front of the wait now delivers the update across the wait's own row, and the wait that follows keeps its original deadline, so an update does not extend a timeout the workflow asked for once. It was never specific to 0.6.0: the same behaviour is in v0.5.0, and `sleep` was never affected. **Not covered by this change:** `wait_for_event` (its poll sits in front of a claim record, not in front of the wait), and a wait that is HELD in memory inside the residency window (an update sent to it is handled when the wait ends, at most the window, 5 minutes by default, later). A run already stuck in this state needs no repair: its next wake (a signal, a timeout, an update of another name) handles the update that is waiting, and sending it any signal wakes it at once.
