section: fixed
---
- **An update sent to a run that is waiting is handled when the run wakes for it, and no longer only when the wait ends (cleat#4511).** Before this fix, an update that arrived while a run was waiting in `AwaitSignals`, `AwaitPromise` or a child await was not handled until that wait ended. Measured on a real 0.6.0 worker with a guest in one 15-second `AwaitSignals`: the update's promise stayed `pending` until the wait ended. When it ended, a guest that went on to another wait handled the update there (about 12 seconds after it was sent), and a guest that returned right after the wait never handled it: the update was rejected as the run completed, with `reached terminal status "done" with this update still pending, so it can never be handled`. While the first update was pending, a second update of the same name was refused with `409 update_already_pending` (measured separately, with a one-hour wait). For a wait of hours or days, that is the whole wait. The update is now handled at the wait when the run wakes: the handler runs, the caller's promise resolves, and the run goes back to the same wait, which keeps its original deadline, so an update does not extend a timeout the workflow asked for once. Waiting in short slices was the workaround, and still works. Measured with a real guest and worker for `AwaitSignals`, and at the engine level for the four other waits (`AwaitPromise`, `AwaitChild`, `AwaitAllChildren`, `AwaitAnyChild`); a durable `Sleep` was never affected. It is not new in 0.6.0: it reproduces on v0.5.0 for `AwaitSignals` and the three child waits (`AwaitPromise` was not run there). **Not covered:** an update sent to a run waiting in `WaitForEvent` is not handled until the wait returns (cleat#4539).
