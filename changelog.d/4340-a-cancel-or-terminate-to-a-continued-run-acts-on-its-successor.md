section: upgrade
---
- **A cancel or a terminate sent to any run of a continue-as-new chain acts on the CURRENT run, and a cooperative cancel no longer vanishes when the run continues (cleat#4340).** `POST /api/workflows/<id>/cancel` (pre-emptive or cooperative) and `POST /api/dead-letters/<id>/terminate` addressed to a run that has continued as new used to act on that old run's own row: a pre-emptive cancel or terminate was refused as already settled (`409`) although the workflow was still running, and a cooperative cancel set a flag nothing read and answered `200`. They now act on the **end of the chain**, exactly once, and the `200` adds **`workflow_id`** (the run acted on) and **`forwarded_from`** (the run you addressed), both absent when the verb acted where it was addressed. A cooperative cancel already requested on a run that then continues is **carried to its successor**, with its reason; before, the successor started un-cancelled. A cancel that races the continue lands on exactly one run and leaves no open successor. A chain whose current run is already settled still answers `409`, and the message now names that run. **Breaking, and deliberate: a cooperative cancel (`POST /api/workflows/<id>/cancel` without `"preemptive"`) to a chain whose current run is `done` or `cancelled` now answers `409 {"detail":"state_conflict"}`, where it used to answer `200 {"status":"cancellation_requested"}` and store a request no run would ever read.** That is the rule a signal follows; a `failed`, `terminated` or `dead_lettered` current run still accepts, because an operator can reopen it and the request is then read. The pre-emptive cancel and terminate already refused a settled run and still do. A client that cooperatively cancelled `done` workflows and read the `200` as success will now see a `409`. No request body changed, and a client that does not read the new reply keys sees what it saw before. See [workflow lifecycle](docs/reference/workflow-lifecycle.md).
