section: upgrade

- **A cancel or a terminate sent to any run of a continue-as-new chain acts on the CURRENT run, and a cooperative cancel no longer vanishes when the run continues (cleat#4340).** `POST /api/workflows/<id>/cancel` (pre-emptive or cooperative) and `POST /api/dead-letters/<id>/terminate` addressed to a run that has continued as new used to act on that old run's own row: a pre-emptive cancel or terminate was refused as already settled (`409`) although the workflow was still running, and a cooperative cancel set a flag nothing read and answered `200`. They now act on the **end of the chain**, exactly once, and the `200` adds **`workflow_id`** (the run acted on) and **`forwarded_from`** (the run you addressed), both absent when the verb acted where it was addressed. A cooperative cancel already requested on a run that then continues is **carried to its successor**, with its reason; before, the successor started un-cancelled. A cancel that races the continue lands on exactly one run and leaves no open successor. A chain whose current run is already settled still answers `409`, and the message now names that run. No request body changed, and a client that does not read the new keys sees what it saw before. See [workflow lifecycle](docs/reference/workflow-lifecycle.md).
