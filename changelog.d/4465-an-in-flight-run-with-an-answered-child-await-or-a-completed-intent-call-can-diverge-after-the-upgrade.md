---
section: upgrade
---
- **A run in flight across this upgrade can diverge at a call whose request used the durable clock after an answered child await or a completed write-ahead-intent call; let in-flight runs finish before upgrading (cleat#4465).** The fix stores the answer's time for every answer written from now on. It cannot repair a row written before it: the row holds one time, and for an `await_child` or `await_all_children` that was answered over a pending record, or a write-ahead-intent call completed over its intent row, that time is when the await or the call STARTED, with nothing in the row that says when it was answered. So a run whose history already holds such a record, followed by a `call` or `plugin_call` whose request was built from the durable clock (`Now()` in the request body), replays a clock earlier than the one it recorded the request with, and the request comparison (cleat#4424) refuses it with `replay divergence at step N: ... with a different request`. A history in which the answered await or completed call is the LAST record, or is followed only by calls whose requests do not carry the clock, replays as before. Before upgrading, let those runs finish, or terminate and restart them; there is nothing to do for a run that starts after the upgrade. Every history written before this change carries the old timestamps, whatever build wrote it. A history that was already compacted keeps the timestamps compaction copied, so it keeps them after the upgrade too. **Embedders that do not pass `WithWorkflowStartTime`** (the worker does) seed a replay's clock from the first record's timestamp: when a run's FIRST step is an answered child await or a completed intent call, a `Now()` read before that step now reads later on a replay than it did live, by about how long the step was pending (measured at +131 to +148 ms with two 60 ms waits, against +0 to +2 ms before the change). The worker passes `WithWorkflowStartTime`, so worker deployments are unaffected.
