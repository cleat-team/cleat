- **A run held through a wait now publishes the query state it set before the wait, instead of showing a client nothing for the whole hold (cleat#4358).** With `--resident-max-runs` above zero, a run that is held never returns to the worker, and the worker wrote a run's query state only when its execution returned, so `GET /api/workflows/<id>/query` returned nothing the guest had set before its wait until the run suspended or finished. The example agent's approval wait polls with 2 s sleeps, each held, so the `awaiting_approval` status it sets once before the first poll was never visible. The state is now written, fenced like the finalize it stands in for and sealed when the deployment seals query state, just before a run is held, and only when it has changed since the last write; **if it cannot be written the run is not held** and suspends as it does with residency off, which writes it. A run with unflushed events under `noPerStepFlush` is likewise not held. Residency is opt-in until #4351, so nothing that runs today changes unless `--resident-max-runs` was set; a new method, `WorkflowStore.PublishQueryState`, is added to the store interface, so a custom `WorkflowStore` implementation needs it.
