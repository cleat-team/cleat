---
section: upgrade
---
- **Stop every 0.6.0 worker before starting 0.6.1, and do not roll back below 0.6.1 once a run has taken an update while suspended in a wait (cleat#4511).** 0.6.1 records such an update with a marker that is part of the event's checksum, and a 0.6.0 worker does not know the marker. A 0.6.0 worker that claims a run carrying one fails the replay's checksum verification BEFORE any workflow code runs (`checksum verification failed: ... checksum mismatch`) and the run goes to `failed`. Measured on a real database with a 0.6.0 worker (70e51029): the failure is terminal for that worker, and waking the run again on a 0.6.1 worker does not bring it back. An operator can recover the run on 0.6.1 with the admin `re-replay` (`--enable-admin-api`): it completed the run in the case measured, with both updates replayed, but `re-replay` is known to fail for other histories (cleat#4535), so treat it as a try and not a guarantee. Running 0.6.0 and 0.6.1 workers side by side during an upgrade is what exposes a run to this, which is why every 0.6.0 worker is stopped first. Only runs that received an update while suspended in a wait, after the upgrade to 0.6.1, are affected; every history written before it replays as it did.
