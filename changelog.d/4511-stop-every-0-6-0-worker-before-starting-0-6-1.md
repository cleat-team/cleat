---
section: upgrade
---
- **Stop every 0.6.0 worker before starting 0.6.1, and do not roll back to 0.6.0 once a run has taken an update while suspended in a wait (cleat#4511).** 0.6.1 records such an update with a marker that is part of the event's checksum, and a 0.6.0 worker does not know the marker. A 0.6.0 worker that claims a run carrying one fails the replay's checksum verification BEFORE any workflow code runs (`checksum verification failed: ... step 2: checksum mismatch`), and the run goes to `failed`. Only runs that received an update while suspended in a wait, after the upgrade to 0.6.1, are affected; every history written before it replays as it did. Running 0.6.0 and 0.6.1 workers side by side is what exposes a run to this, which is why every 0.6.0 worker is stopped first.

  **Measured on one PostgreSQL, with real worker binaries (0.6.0 at 70e51029; the 0.6.1 worker was a build of this change's first version, before its review fixes). A run that failed this way:**

  - **Does not come back when it is woken again on 0.6.1.** A `done` signal was already pending and the 0.6.1 worker claimed the run: it stayed `failed` (3 of 3 runs).
  - **Did complete under the admin `re-replay` in ONE history shape, on 3 of 3 runs.** The shape: a Go workflow that handles two updates inside one `AwaitSignals` loop (`update_handler, await_signals, update_received, update_completed, await_signals, update_received, update_completed, await_signals`), whose next step after its last wait is the end of the workflow, with its `done` signal already pending. The run reached `done` each time; the result, read on the last two, was `{"n": 2}`, both updates replayed. The commands, on a worker started with `--enable-admin-api`: `POST /api/admin/instances/<run id>/re-replay`, headers `Authorization: Bearer <api key>` and `X-Confirm: re-replay`, body `{"generation": <the run's current lease generation>}`; the answer was `200 {"status":"queued_for_replay"}`.
  - **Was NOT shown to complete in any other shape, and cleat#4535 shows two where `re-replay` fails.** There, on develop at 460bade1 (before this change, so the failure was produced by corrupting one stored checksum on a suspended run, not by a rollback), `re-replay` answered `200`, the run was claimed again and failed again with `replay divergence at step N: expected call, got admin_action`, in both histories tried: a call, an `await_signals` of one hour, then a second call; and a call, a four-second sleep, then a second call. What those two have that the recovered one does not is a guest call after the wait. That is an observation about the three histories, not an explanation: why one completes and two do not was not established.
  - **Not measured at all:** `re-replay` of a rolled-back run in any other history shape, on MySQL or SQL Server, or with other updates still pending.

  So treat a rollback as not survivable for the runs that took such an update: re-replay may recover a run and you cannot tell in advance which. Runs that did not take an update inside a wait are not affected.
