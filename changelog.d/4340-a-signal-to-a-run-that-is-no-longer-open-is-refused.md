section: upgrade
---
- **A signal sent to any run of a continue-as-new chain is delivered to the CURRENT run, and one sent to a run that can never be reopened is refused where it used to be accepted and lost (cleat#4340).** A signal is addressed to a workflow, not to a run. `POST /api/workflows/<id>/signal` to a run that has continued as new used to store the signal under that run's own id, where nothing read it, and answer `200 {"status":"delivered"}`; it now delivers it to the **end of the chain**, exactly once, and the `200` adds **`workflow_id`** (the run that now holds it) and **`forwarded_from`** (the run you addressed), present only when forwarded. A signal already stored on a run (sent, not yet read) when it **continues as new is carried to its successor**, in order, in the transaction that completes the old run; a signal that races the continue lands on exactly one run. A chain whose **current run** is `done` or `cancelled` answers **`409 {"error":…, "detail":"workflow_not_open", "status":"done"|"cancelled", "continued_to":"<run>"}`** and stores nothing (`continued_to` is present only when the run addressed had continued, and names the chain's last run). The refusal is the same under an `Idempotency-Key` and does not spend the key. A run that does not exist or belongs to another tenant is still `404`. **What to do:** a caller that relied on `200` for a run that had finished or been cancelled was having its signal dropped silently; treat `409` as "the workflow is over". A caller that held the id of an early run and signalled it no longer needs to chase `continued_to`. Inside a workflow, `SignalWorkflow` to a target that is closed for good now returns the existing not-found outcome instead of success, and a plugin sees `plugin.ErrWorkflowNotFound` (so an event-trigger awaiter registered for the run is dropped, as for a missing one). **Unchanged, with one wording change:** a `failed`, `terminated` or `dead_lettered` run can be reopened under the same id (`retry`, `re-replay`) and would then read a signal stored before the redrive, so signals to those runs, or to a chain whose current run is one of them, are still accepted and stored. The reply is the same `200`, but `status` is now `"stored"` instead of `"delivered"`, with `run_status` and a `detail` saying the run reads it only if it is retried or re-replayed; a client that compares `status` to `"delivered"` should handle `"stored"`. **Known issue (sharding, experimental):** a signal addressed to a successor by its own id can be routed to a shard that does not hold it; a signal to the first run of a chain is not affected. Whether `failed`, `terminated` and `dead_lettered` should refuse instead is cleat#4345.
