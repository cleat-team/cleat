section: upgrade
---
- **A history with a call recorded after a pending child await is now refused at replay instead of running that call a second time (cleat#4285).** Who is affected: **in-flight workflows whose guest ignored a child-await suspension** (a guest that swallowed the suspension and went on to make a call: Java before 0.6.0, and any SDK or guest that returns the suspension as an ordinary value or catches the exception). Such a workflow has `[a child await with an empty response, a call it made afterwards]` in its history. Before 0.6.0, when the child finished and the workflow resumed, replay left that call unread and the call ran **again**: a service call that must happen once happened twice. Now `await_child`, `await_all_children` and `await_any_child` stop at the pending record with a replay divergence, consuming nothing and running nothing: *"history written by a guest that ignored a child-await suspension before 0.6.0 (cleat#4285); replaying it would run that call a second time. Terminate or reset the workflow."* **Terminate or reset it**, as the message says: the call already ran once, and re-entering replay to skip it is a recovery tool 0.6.0 does not have. **To find them before upgrading, on PostgreSQL:** run `scripts/find-histories-with-a-call-after-a-pending-await.sql` (it was run against workflows written through the store: a known positive is listed, and a defer drain's own call, an answered await, a call recorded BEFORE the await and a finished workflow are not). **What it cannot do:** run it as a role that bypasses row level security (`event_history` is `FORCE ROW LEVEL SECURITY`, and a filtered role returns nothing, which reads like "nobody is affected"); it was not written for MySQL or SQL Server, and was not exercised with `--encrypt-sensitive-payloads`; it cannot see events a compaction already folded away, which the replay does not refuse either (compaction does not carry the drain stamps, so those records are unknown, not stale); and it may list a drain written before cleat#1155, whose records carry no stamp. **Narrower than "any later record" on purpose:** only a later record that is a call's *effect* (the engine's own `stoppableFirstEvents` list) counts, not an admin audit row or a delivery. **New histories are not affected:** since #4295 the host refuses the call when it is made, so nothing is recorded after a pending await. This also changes when a workflow whose child is still running at the resume is told: it now fails at the pending await, where before its call was refused and it suspended quietly until the child finished and then ran the call again.
