section: upgrade
---
- **A history with a call recorded after a pending child await is now refused at replay instead of running that call a second time (cleat#4285).** Who is affected: **in-flight workflows whose guest ignored a child-await suspension** (a guest that swallowed the suspension and went on to make a call: Java before 0.6.0, and any SDK or guest that returns the suspension as an ordinary value or catches the exception). Such a workflow has `[a child await with an empty response, a call it made afterwards]` in its history (an `await_child` that carries an error is an answer, a failed child the guest handled, and is not pending: that history is healthy and is not refused). Before 0.6.0, when the child finished and the workflow resumed, replay left that call unread and the call ran **again**: a service call that must happen once happened twice. Now `await_child`, `await_all_children` and `await_any_child` stop at the pending record with a replay divergence, consuming nothing and running nothing: *"history written by a guest that ignored a child-await suspension before 0.6.0 (cleat#4285); replaying it would run that call a second time. Terminate or reset the workflow."* **Terminate or reset it**, as the message says: the call already ran once, and re-entering replay to skip it is a recovery tool 0.6.0 does not have. **To find them before upgrading, on PostgreSQL:** run `scripts/find-histories-with-a-call-after-a-pending-await.sql` (a test writes 1,215 history shapes through the store, decides each with the engine's own await calls AND with this SQL, and requires the two sets to be equal; a known positive is found, and a defer drain's own call, an answered or failed await, a call recorded BEFORE the await and a finished workflow are not). **What it cannot do:** run it as a role that bypasses row level security (`event_history` is `FORCE ROW LEVEL SECURITY`, and a filtered role returns nothing, which reads like "nobody is affected"); **MySQL and SQL Server: no script provided**, and it was not exercised with `--encrypt-sensitive-payloads`; it may list a drain written before cleat#1155, whose records carry no stamp. **A NAMED GAP: a bad history that was already compacted is NOT refused, and this script does NOT find it.** Compaction deletes the folded events from `event_history` and does not carry the drain stamps, so those records are unknown rather than stale, and refusing an unknown would fail a healthy drain. The call recorded after such a compacted pending await can still run twice, exactly as before; there is no script for them. **Narrower than "any later record" on purpose:** only a later record that is a call's *effect* (the engine's own `stoppableFirstEvents` list) counts, not an admin audit row or a delivery. **New histories are not affected:** since #4295 the host refuses the call when it is made, so nothing is recorded after a pending await. **A workflow whose child is still running at the resume also fails now, at the pending await**, where before the host refused its call and it suspended quietly until the child finished and then ran the call again. That is the same outcome reached sooner, and with no extra store read: the finished-child case is what that workflow becomes the moment the child finishes.
