- **A Python or C# workflow that registered a defer and then slept ran the defer's cleanup at its first suspension, and could not resume (cleat#4194).** The component path drained a guest's defer table at EVERY suspension; only a defer segment is meant to drain, and the core-module path already guarded the call with `deferPhase`. So `h.defer_func(cleanup); h.call(...); h.sleep(5)` made the cleanup call while the workflow was merely waiting, recorded it in history at the step the workflow's next call belonged to, and the resumed run failed with `replay divergence at step N: workflow called ... but history has <the cleanup>`. **Present in 0.4.0 and 0.5.0** (the unconditional call arrived on 2026-09-04 with the stop-is-unrepresentable change, #667; measured by reading `v0.5.0:engine/component_cgo.go`, not by running that release). The drain is now taken only in a defer segment (`deferPhase`) and when the suspension is a **continue-as-new**, which ENDS the run: a component guest that raises its suspend sentinel after `continue_as_new` (the SDK's own pattern) does not drain by itself, so without that second condition its cleanup would never run, where a Go guest runs it once. Defer segments (a failed, terminated or killed run's cleanup) are unchanged. Held, for Python and for C#, by a sleep test (the cleanup does not run at the suspension) and a continue-as-new test (it runs exactly once); each is red under the mutant that breaks its side.
