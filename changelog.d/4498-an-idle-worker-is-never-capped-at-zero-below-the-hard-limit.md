- **A worker at a low `--concurrency` could cap itself at 0 and claim nothing while idle, with nothing in the log (cleat#4498).** Between `--memory-soft-limit` and `--memory-hard-limit` the cap is `round(--concurrency × (1 − pressure))`, which is 0 for any pressure above 0.5 at `--concurrency 1` (above 0.75 at 2). On macOS, where the memory source is the Go heap, a worker at `--concurrency 1` under load stalled for 8 to 74 s with `cleat_concurrency_limit` at 0 and nothing in flight (5 of 10 runs; 0 of 8 with the limits at 1.0). It is unchanged since v0.5.0. The cap is now never below 1 until the hard limit, where it is 0 as before; the dispatcher already subtracts what is in flight, so this is one workflow at a time, not a second on top of a running one. The cgroup v2 reading now subtracts inactive file cache (`memory.stat` `inactive_file`, the kubelet's working set), which the raw `memory.current` counted as use, so a container that has only read files no longer reads as full. The worker logs a WARN when pressure holds its cap at 0 or at the floor (at most one line per 30 s) and an INFO when it lets go. `--memory-soft-limit`'s help and `docs/operations/tuning.md` said it "stops claiming new work"; they now say what it does.
