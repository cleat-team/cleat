- **A heartbeat call resumed after a lost worker now carries the idempotency key of the step its first incarnation started at, not a later one (cleat#4247).** `DurableCallWithHeartbeat` records one `heartbeat` event per tick. When a worker was lost mid-call, the reclaimed run replayed those heartbeats, which advanced the step, and then ran the call again with an idempotency key derived from the step AFTER them: a different key from the first incarnation's, so a service that deduplicates on the key performed the call a second time. The replay now remembers the step of the first heartbeat it consumes (the step the call started at, since nothing else is recorded while it runs) and the fresh call derives its key from that; the events it records still take the session's own steps in order. A call that was lost before any heartbeat was recorded has nothing to recover and is unchanged. This is the same rule `DurableCallWithRetry` has followed since cleat#1145. Whether a given service sees a duplicate depends on the caller forwarding the key and the service deduplicating by it; what changed is the key the engine hands the caller.
