section: upgrade
---
- **`--component-precompile` is ON by default: a Python or C# workflow is compiled in a short-lived child process, so the worker does not keep the compile's memory (cleat#4397). Turn it off with `--component-precompile=false`.** Measured on a real worker in a 2 GiB container with nine distinct Python components: compiling in the worker retained 198 to 308 MiB for each of the first four further components and 44 to 76 for each of the next three (mean 175) and the container was OOM-killed on the ninth (peak 2013 of 2048 MiB), where with the child the same run completed at a peak of 1159 MiB; six components arriving at once killed the in-worker compile within 17 seconds and completed in 41 seconds with the child. **A worker now compiles ONE component at a time**, in the child or in-process, so a burst of runs of distinct components queues instead of compiling together. A child that fails for an ordinary reason falls back to the in-process compile (still one at a time) and is counted on `cleat_component_precompile_fallbacks_total{reason}`; a rate there means the child is failing systematically and the worker is compiling in-process, so read the WARN for the cause. A single run of each configuration on one arm64 machine; x86-64 is not measured. The first Python compile adds about 490 MiB to a worker and most of it stays, and each of the first four further distinct Python components retains 198 to 308 MiB more and each of the next three 44 to 76 (mean 175); loading the child's artifact instead leaves the worker at about 68 MiB (measured in a container, 2026-11-23). It lowers the steady state, **not the compile peak**: the child shares the worker's memory limit. At a 512 MiB limit, a stated tight configuration, the worker compiles its first Python workflow with about 60 MiB to spare (arithmetic, not a measured anon peak); with the flag off it is OOM-killed (3 of 3). `--component-precompile-parallel` (`auto`: parallel unless the memory limit is under 1 GiB) and `--component-precompile-timeout` tune it. A child that fails for an ordinary reason falls back to the in-process compile. A child that is SIGKILLed (the OOM killer) is **not** answered by compiling in the worker, which would kill it: the run is released with a back-off, not failed, no further child is started for that component for 5 minutes, and the worker logs an ERROR and counts `cleat_workflow_releases_total{check="component_compile_refused"}`. Where `memory.oom.group` is 1 (Kubernetes' default on cgroup v2, per its documentation, not measured here) an OOM kill takes the whole container, and the worker warns at start-up. See `docs/reference/worker-config.md`.
