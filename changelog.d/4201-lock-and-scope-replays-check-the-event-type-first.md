- **FIX: a replayed `acquire_lock`, `release_lock` or `set_scope` over a recorded event that belonged to another call swallowed that event (cleat#4201).** The three replays advanced the step before they checked the event's type, so a guest that reached one of them where the history held a different event (a code change between runs, or non-determinism: the cases replay divergence exists for) got error code 1, was moved one step on in the history, and reported no divergence and no replay-failure metric. They now check the type first, leave the step where it was and report the divergence, as every other replay checked here already did. Measured on a session in replay over a `create_promise`: the control (`resolve_promise`) left `stepCount` at 0 and the three left it at 1; after the fix all four leave it at 0 and each call over its own event still consumes exactly that step. Not measured: what the guest's next call did against the misaligned history. A loose scan (`advanceReplayStep(` followed by an event-type comparison within a few lines, not before it) matched 8 more replay blocks that were NOT read, and are filed as cleat#4206 for the same check.
