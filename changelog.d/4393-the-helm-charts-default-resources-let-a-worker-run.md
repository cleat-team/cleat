---
section: upgrade
---
- **The Helm chart's default resources are larger, and its autoscaler no longer scales on memory (cleat#4393).** The defaults were requests 100m / 128Mi and limits 500m / 512Mi, which could not run a Python workflow (a Python component compile was OOM-killed at a 512Mi limit and took 11.4 s at 500m of CPU, measured 2026-11-23) and which pinned the HPA at `maxReplicas`, because 80% of a 128Mi request is below what a warmed worker uses. They are now requests 500m CPU / 2Gi memory and limits 2 CPU / 2Gi (a worker reserves its memory: the request equals the limit), `autoscaling.targetMemory` is unset (the HPA renders a memory metric only when it is set), and `values.yaml` says what a worker uses and why. **An install that sets both `resources.requests` and `resources.limits`, and one that sets `autoscaling.targetMemory`, is unaffected. An install that sets only a LIMIT below the new default request (memory under 2Gi, CPU under 500m) is now refused by `helm template` and `helm upgrade`**: Helm merges your values over the chart's, so the default request stays above your new limit, and Kubernetes would reject the pod. The chart says so at render time and names what to set: set `resources.requests` as well. An install on the defaults will get pods that request 2Gi and 500m each, so with `minReplicas: 2` the cluster needs 4 GiB and 1 CPU free to schedule them, and the pre-upgrade migration Job (which shares `resources`) asks for another 2Gi and 500m while the old pods are still running. Set `resources.requests` and `resources.limits` to the old values to keep the old footprint, and expect a Python component compile to be OOM-killed in it.
