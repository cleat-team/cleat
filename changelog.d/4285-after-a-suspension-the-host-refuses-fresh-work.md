section: upgrade
---
- **Once an execution has suspended, the host refuses every call that would start fresh work, so a guest that ignores the suspension can no longer run a service call, a plugin call, a child start or any other effect twice (cleat#4285).** A guest is told to stop when a child await, a wait, a stop or `continue_as_new` suspends the run, and some do not: an SDK returns the suspension as an ordinary value, or the guest catches the exception or discards the error. Every call such a guest then made was recorded after the pending await and ran again on resume, the worst case being an outbound service call. Those calls now run nothing, record nothing and keep the first suspension, and answer the word their own SDK decoder already recognises (the stop word; `1 << 62` for the child awaits; an ordinary error for `list_crons` and `release_lock`; the sleep's own suspend status). A defer drain is exempt when the host runs it, and when the guest runs its own only if that drain began before the suspension or the suspension is a `continue_as_new`; a guest wrapper that runs the defers AFTER a wait suspension (because the guest swallowed it) is refused like any other call. **What you may see:** a workflow that kept calling after a suspension now gets a refusal where it used to get a result, and the host logs `a host call was made after the workflow had already suspended and was refused` naming the call; the call is then no longer made twice. A history already written by such a guest still replays as recorded; this changes only what a live segment does after it has suspended. See ABI.md, *Suspension sentinel*.
