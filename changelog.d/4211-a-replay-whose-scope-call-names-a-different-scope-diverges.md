- **A replay whose `set_scope` call names a different virtual object than the event recorded at that step now fails as a divergence (cleat#4211, cleat#4152).** The replay accepted the FIRST `scope_acquired` record at a step whatever scope it named, and adopted the scope the guest asked for on the strength of a record for another one; and when a run of failed attempts was followed by a record for another scope or another event type, it returned a bare error, consumed the failed attempts and reported nothing. A workflow whose code changed which scope it takes at a step that is already in its history is now stopped at that step with a `replay divergence` error naming what was asked and what was recorded, counted in `cleat_replay_failures_total`, with the history left unread for the call it belongs to. Every `scope_acquired` event carries the scope key, on its error paths as well as its success path, in every release from v0.1.0 to v0.5.0 (the three records are written with it in each tag, read by parsing the record literals; the key is built as `vo:<type>:<instance>` the same way in all of them, and it has been persisted since v0.1.0), and it is kept through compaction and through the PostgreSQL, MySQL and SQL Server stores (round-tripped against all three, including a run of failed attempts followed by the acquisition), so a history written by a released version matches the code that wrote it. Nothing else about the call changes: taking a scope is refused in a defer segment's body, after a shutdown and after an event that could not be written exactly as before, and clearing a scope (`set_scope` with both names empty) records nothing and is never refused.
