section: fixed
---
- **A run suspended on a timer is claimed when its timer comes due, not at the next tick of an idle worker's poll backoff (cleat#4491).** An idle worker sleeps up to six `--poll` intervals between empty claims, and only a workflow finishing on that worker, a PostgreSQL NOTIFY, or finding work cut the sleep short; a timer coming due sent none of them. At the default `--poll 500ms` a suspended timer therefore fired up to 3 s late: measured on PostgreSQL with one idle worker and residency off, a 2 s sleep resumed at a p50 of 1127 ms past its time (rep medians 1106 to 1129 ms) and a 12 s sleep at 1657 ms. The worker that suspends a run now schedules a poll for the wake time it wrote (a bounded number of timers, none for a wake more than 15 minutes away), and the same measurement reads 79 ms at p50 for the 2 s sleep (rep medians 73 to 95 ms, the resume itself) and 91 ms for the 12 s one; a timer held in memory is unchanged at about 12 ms. Not changed: a suspended signal wait on MySQL and SQL Server, which the same backoff delays and which this fix does not touch, and a run another worker suspended, which that worker's own poll serves.
