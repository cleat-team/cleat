- **`cleat vet` warns about a monotonic-clock read in a Python workflow (PY016), and the docs now say the monotonic clock is real elapsed time in every language (cleat#4396).** A Python or C# workflow reads the host's own monotonic clock, and a replay of the same workflow reads different values: measured on componentize-py 0.25.1, two runs of one workflow id read 0.5029 and 0.5021 seconds for the same `time.sleep(0.5)`, and a `while time.monotonic() - t0 < 0.5` loop ran 41 and then 42 iterations. That is not changed here: the clock stays real, because it cannot be pinned on the component path (a shadow of `wasi:clocks/monotonic-clock` replaces its `subscribe-*` functions too, whose pollables the host cannot supply). What changes is that the tooling says so. PY016 is a warning, never an error, for `time.monotonic`, `monotonic_ns`, `perf_counter`, `perf_counter_ns`, and `time.sleep` written through an alias (`import time as t`, `from time import sleep`); a plain `time.sleep` was already the PY004 error, whose message now also says that the sleep blocks the worker for its whole duration and the instance timeout does not interrupt it (cleat#4403). Use `h.now()` and subtract two readings for an elapsed time, and `h.sleep()` for a sleep. C# already refused `Stopwatch`, `Environment.TickCount[64]` and `Thread.Sleep`, and Go `time.Now` and `time.Sleep`. **Not flagged:** Java's `System.nanoTime`, and there is no TypeScript vet. `docs/determinism.md` has a new section with what was measured and what was read from the code, and the Python README's `time` row, which said `time.sleep()` "is not available", now says what was measured.
