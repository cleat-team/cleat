section: upgrade
---
- **The record that tells a timed-out await from an answered one is written from this version on; a history recorded before it keeps the old answer (cleat#4277).** The shape that stays ambiguous is an `await_promise` event followed at the very next step by a `promise_resolved` or `promise_rejected` event of the same promise, with no `first_read` in the settlement. A replay of one still hands the await the resolution, as it always did, even when the original run had been told it timed out. **To find the runs where it could matter:** look for that pair where the settlement's `timestamp_ms` is later than the await's `timestamp_ms` plus its `timeout_ms`. A settlement recorded inside the await's own window is an answer to it and is never the other shape. The test is a superset: a wake that found the promise already settled after the await's deadline records the same pair and is not affected. Only awaits made after the upgrade are recorded with the marker. The marker is a new field of the settlement event, inside its checksum only when it is set, so no event written before this version changes its checksum. During a rolling upgrade an older worker that replays a history written by a newer one does not read the field and gives the old answer for that shape, so a workflow that branches on an await's timeout can see the two answers differ until every worker is upgraded. Nothing in the engine or the CLI verifies event checksums on its own (`VerifyWorkflowEvents` has no caller outside the stores), so an older worker is not expected to report an integrity error for the new field; that was not run.
