- **A run that answered a child await, or completed a write-ahead-intent call, replayed with the clock of the moment the await or the call STARTED, so a later call whose request carried `Now()` diverged on replay (cleat#4465).** A history record's timestamp is rebuilt from `event_history.created_at`, and a replay's `Now()` is made from it. An `await_child` or `await_all_children` that found its child still running is recorded EMPTY and answered later at the SAME step, by an upsert over the pending row; a write-ahead-intent call is recorded pending before the call and completed after it, by an UPDATE of the same row. None of those statements set `created_at`, so the row kept the START time while the live run had read the time of the ANSWER. A guest that read `Now()` after the await and put it in the request of its next `call` recorded one request and, on the next wake, replayed another, and the request comparison of cleat#4424 refused it: `replay divergence at step N: call asked for something other than the call recorded there: call S.O with a different request`. clew-dogfood's candidate-pin run hit it on `4de6096f`, as 46 failures in its `slice e2e`. Every answer-over writer now stores the answer record's own time in `created_at`: the five Postgres statements (the per-event flush, the one-event and the many-event batch append, the adaptive flusher's batch and its retry), the MySQL upsert (under the same pending marker as the rest of its assignments), the SQL Server `MERGE`, and `CompleteCallIntent` on all three dialects. The event checksum does not cover the timestamp, so no checksum changes and a chain recorded before still verifies. An `await_promise` was never affected: its settlement is recorded at a new step, and its deadline is read from the pending await's own record, which this change does not touch. Two things a reader of a history will see. A pending child await that is re-recorded on a later wake (its child was still running) now carries the time of the LATEST wake and not the first. And a history compacted before the upgrade keeps the timestamps compaction copied from it (compaction copies `TimestampMs` from the loaded history), so only new compactions carry the corrected ones. The retention bound on replaying a pending intent under its original idempotency key reads a row that was never completed, so it is not moved by this.
