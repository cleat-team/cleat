section: fixed

- **A worker refuses to compile a component in its own process when the container has too little memory left, and releases the run instead of dying (`--component-compile-min-headroom-mb`, cleat#4397).** What a compile needs depends on the component: 800 MiB for a Python-sized one, scaled by size down to 256 MiB for a small C# workflow (measured: a C# compile peaked at +11 to +118 MiB, Python at about 500 MiB of scratch plus up to about 300 kept (198 to 308 for each of the first four further components, then 44 to 76)). **A refusal usually lasts until a restart or a larger limit**, because the memory a compile keeps does not come back. Serialising compiles removes the simultaneous peak and not the retention (198 to 308 MiB for each of the first four further distinct Python components and 44 to 76 for each of the next three (mean 175), for good), so a worker that compiles in its own process (the fallback after a failed `--component-precompile` child, and every compile with `--component-precompile=false`) ran out of memory on about the seventh distinct component at a 2 GiB limit: killed in one measured run and sitting at the limit in another. Now it looks at the memory left, from the same cgroup reading as `--memory-soft-limit`, and below the minimum it does not compile: the run is released, not failed, retried after `--component-precompile-refusal-window`, components already compiled keep running, and the refusal is an ERROR and `cleat_workflow_releases_total{check="component_compile_refused",reason="low_headroom"}` (the existing killed-child case is now `reason="child_killed"`). **This is a degraded mode, not a full-speed one:** a worker under memory pressure refuses new components until memory comes back or another worker takes the run. `0` turns it off; with no cgroup v2 limit it reads the host's memory and warns. The 800 is a measured estimate for Python and the scaling is a fit through two measured languages (see the reference).
