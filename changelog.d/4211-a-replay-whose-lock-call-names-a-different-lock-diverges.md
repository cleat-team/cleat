- **A replay whose `acquire_lock` or `release_lock` call names a different lock than the event recorded at that step now fails as a divergence (cleat#4211, cleat#4152).** These replays used to match on the event type alone: a call asking for lock `b` over a record for lock `a` was handed that record's answer and consumed it, so the workflow was told it held `b` while the store held `a`, and went on inside a critical section it had not entered. A workflow whose code changed which lock it takes or gives back at a step that is already in its history is now stopped at that step with a `replay divergence` error naming what was asked and what was recorded. Every event these two calls write carries the lock key, on its error paths as well as its success path, in every release from v0.3.0 to v0.5.0 (the lock calls and the stores' persist and load are byte-identical across those tags, and the key has been persisted and loaded back since v0.1.0), and it is kept through compaction and through the PostgreSQL, MySQL and SQL Server stores (round-tripped against all three), so a history written by a released version matches the code that wrote it. Nothing else about the two calls changes: `release_lock` is still never refused, including in a defer segment's body, after a shutdown and in a defer draining on a shutting-down worker, where `acquire_lock` is refused, and that is now declared on the call and no longer an entry in a list of exemptions. `set_scope` has the same gap and is the next call moved; cleat#4211 stays open for it.
