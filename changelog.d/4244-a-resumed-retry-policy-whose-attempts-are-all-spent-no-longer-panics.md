section: fixed

- **A retried call that has no attempt to make no longer panics the worker (cleat#4244).** A retry policy with zero or negative max attempts is now refused instead of crashing the worker: `DurableCallWithRetry` with `maxAttempts` below 1 never entered its retry loop, so the terminal event was built from a nil error and the host panicked. The Go SDK reaches it with a `cleat.RetryPolicy` that sets no `MaxAttempts`, and the Rust, Java and Python SDKs pass the value unvalidated. The engine now refuses it at the entry with the same bad-parameter result an unreadable non-retryable list gets, makes no call and records nothing, for a fresh call and a replay alike; a call that is being stopped (a defer segment, a shutdown, a refused event write) still answers the suspend sentinel, which wins over any refusal. The same nil error was reachable on a resume: `DurableCallWithRetry` records each failed attempt, so a worker lost mid-policy leaves attempt events and no terminal event, and the reclaimed run continues from them. When the recorded attempts already equalled the resumed policy's `maxAttempts` (reachable when a worker restarts with a lower `--max-retries` than the run that recorded them), the loop never ran, the terminal event was built from a nil error and the call dereferenced it. The resume now makes no further service call and records the same retries-exhausted failure a policy that ran out normally records, carrying the error of the last recorded attempt. Its error class is not carried (only the message is read back from the attempt event), so the terminal event's class is empty. What a worker did with the panic was not established.
