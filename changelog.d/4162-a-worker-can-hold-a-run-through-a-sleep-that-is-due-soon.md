- **A worker can hold a run on itself through a durable sleep that is due soon, instead of suspending it and replaying it later (cleat#4162). It is OFF unless `--resident-max-runs` is above zero**, and nothing changes for a worker that does not set it. When it is on, a Go guest's `sleep` whose deadline is inside the window keeps its instance and wakes in place when the timer fires, with no claim, no instantiation and no replay; a sleep that is refused for any reason (a language with no measured memory figure, a deadline beyond the window, the run limit or the memory budget reached, the worker over `--memory-soft-limit` or draining) suspends exactly as it always has, and a worker that starts to drain, or reaches its memory hard limit, sends every held run back. New flags: `--resident-max-runs`, `--resident-memory-budget-mb`, `--resident-window-floor`, `--resident-window-cap`, `--resident-replay-multiplier`, `--resident-replay-fixed` and `--resident-replay-per-event`, and four metrics: `cleat_resident_runs`, `cleat_resident_parks_total`, `cleat_resident_refusals_total` and `cleat_resident_evictions_total`. **Limits to read before turning it on:** only Go guests and only durable sleeps are held so far (signals, promises, children and updates are not); the memory charged per held instance comes from measurements of minimal guests and is rounded up, not measured on real workflows; a held run keeps one OS thread, which was measured to about 1,000 held instances and no further; and the multiplier (10x), the window floor (10 s) and cap (5 min) are the owner's starting point and are not measured, so the defaults are deliberately conservative and tuning them on real workflows is cleat#4187. See `docs/reference/worker-config.md` and `docs/design/resident-suspended-runs.md`.
