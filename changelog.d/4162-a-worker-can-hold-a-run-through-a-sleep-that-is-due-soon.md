- **A worker can hold a run on itself through a durable sleep that is due soon, instead of suspending it and replaying it later (cleat#4162). It is ON by default (held runs may be charged 20% of the worker's memory, `--resident-memory-percent`, and `--resident-max-runs` is a ceiling of 1024 on their count; set either to 0 to turn it off)**, and neither number is a measured optimum: 1024 is the largest count the scheduler was measured at, and tuning both on real workflows is cleat#4187. **If a worker dies while it holds runs, their wakes are delayed until the runs are reclaimed: measured with a real kill at the defaults and no shortened lease (three runs on PostgreSQL, an 8 s sleep between two effects), the second effect came 49 to 50 s after the first without the held-run fast path, as in 0.6.0, against 9.2 to 9.5 s with residency off, and every effect still happened exactly once. The reclaim window (about 47 s at the default `--heartbeat`, derived from its formula) plus a reaper tick explains the figure and is not a separate cost on top of it; the held-run fast path, `--held-reclaim-after` (cleat#4275), brings it to about 19 to 20 s (three runs, same setup).** A held run is sent back, and not resumed, when its wait ends and the store no longer has it assigned to this worker (terminated, cancelled or reclaimed while held) or that cannot be established, so a run that is terminated while held cannot act when its timer fires before the next heartbeat. When it is on, a Go, Python or C# guest's `sleep` whose deadline is inside the window keeps its instance and wakes in place when the timer fires, with no claim, no instantiation and no replay; a sleep that is refused for any reason (a language with no measured memory figure, a deadline beyond the window, the run limit or the memory budget reached, the worker over `--memory-soft-limit` or draining) suspends exactly as it always has, and a worker that starts to drain, or reaches its memory hard limit, sends every held run back. New flags: `--resident-max-runs`, `--resident-memory-percent`, `--resident-memory-budget-mb`, `--resident-window-floor`, `--resident-window-cap`, `--resident-replay-multiplier`, `--resident-replay-fixed` and `--resident-replay-per-event`, and four metrics: `cleat_resident_runs`, `cleat_resident_parks_total`, `cleat_resident_refusals_total` and `cleat_resident_evictions_total`. **Limits to read before relying on it:** only Go, Python and C# guests (not Java, Rust or JavaScript) and only durable sleeps and signal waits are held so far; the Python and C# figures are measured on arm64 only; the compiled component is not charged to the budget (the worker's code cache holds it whether or not anything is held), and a hold never outlives its code's cache entry: when the cache evicts a module or component, every held run of it is sent back (promises, children and updates are not held yet); the memory charged per held instance is a measured estimate by language (a guest after it had allocated and dropped 256 MiB), rounded up, and it does not count live data or real workflows (cleat#4377); a held run's wall-clock limits (`--wasm-wall-clock-ceiling`, `--max-workflow-duration`) and its execution fence are paused for the hold and start again at their full duration when it ends, as the next segment of a suspended run's would, so the held time is charged to none of them and the work after the wake gets a full segment (measured on real wasmtime: work 300 ms, a 300 ms wait and work 300 ms under an 800 ms ceiling suspends at the wait with residency off and completes in about 904 ms with it on); a wait whose limit has already ended, or that is due within 100 ms of a deadline that cannot be paused, is not held, and a cancel or terminate ends a held run at once; every `--resident-*` flag is validated at boot even when residency is off; a held run keeps one OS thread, which was measured to about 1,000 held instances and no further; and the multiplier (10x), the window floor (10 s) and cap (5 min) are a starting point and are not measured, so the defaults are deliberately conservative and tuning them on real workflows is cleat#4187. See `docs/reference/worker-config.md` and `docs/design/resident-suspended-runs.md`.
