section: fixed

- **`--memory-soft-limit` and `--memory-hard-limit` are now fractions of the worker's own cgroup's memory limit, not of the cgroup mount's root (cleat#4431).** The monitor read `/sys/fs/cgroup/memory.max` and `memory.current` at the root of the cgroup mount, which is the worker's own cgroup only inside a private cgroup namespace. Under a host cgroup namespace (`docker run --cgroupns=host`, a systemd unit with `MemoryMax=`, some Kubernetes configurations) a worker in a 512 MiB container read a 12,015 MiB total with the host's 5,987 MiB in use (measured on the real worker, 2026-11-23), so its soft limit was near 9.6 GiB and it never stopped claiming work or held-run admission under real pressure. It now considers every cgroup on its own path that has a `memory.max`, measures each against its own `memory.current`, and at every reading uses the one with the least headroom (the same resolver the residency budget uses), and the same container reads 512 MiB. With no limit at any level it reads the host's memory against host-wide usage (`/proc/meminfo`), as a worker with no cgroup does. **A worker in a private cgroup namespace, which is what a container runtime usually gives, reads exactly what it read before.** The worker logs once at start-up what the monitor measures against. **cgroup v1 is still not read** (the monitor falls back to `/proc/meminfo`, the host's memory). If your workers ran under a host cgroup namespace with a container limit, they will now apply `--memory-soft-limit` at 80% of THAT limit, which is the intended behaviour and is much earlier than before: size `--concurrency` accordingly.
