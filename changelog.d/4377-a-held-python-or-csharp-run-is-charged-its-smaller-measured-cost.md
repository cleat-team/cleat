- **A held Python or C# run is now charged 11 MiB or 59 MiB against the resident-memory budget, not 17 or 66 (cleat#4377).** Measured on the fixed builds after a guest has allocated and dropped 256 MiB in 4 MiB chunks, plus 1 MiB for the store and session, rounded up: Python 9.5 MiB (1.3 with none) once built with cleat#4382's dense data segments, C# 57.4 MiB (16.8 with none) at cleat#4378's 8 MiB GC segments. **The saving is much smaller than the idle-instance saving suggests:** at the same budget a worker holds about 1.5 times as many Python runs and about 12% more C# runs, because the GC's large-object heap grows under large-object churn (the same churn on a default-segment C# build reads 65.3 MiB, the old table's 65.7, which is how the old figure came to be understood). **cleat#4386's "49 to 17 MiB" is an idle instance's figure:** a C# workflow that allocates nothing large does cost 16.8 MiB, but an instance that churns large objects stays near 57 MiB (65 on the default GC segments), and the charge covers the one that does. The Go charge is unchanged at 24 MiB, and every figure is still an estimate by language, not a reading. **What is not in them is live data:** wasm memory never shrinks, so a guest that held 100 MiB once keeps it, one for one, and no per-language figure can know that; `--memory-soft-limit`, which reads the cgroup's real use, is the backstop. **This holds only for a component built with those changes:** a Python component built before cleat#4382 costs about 8 MiB more and a C# one built before cleat#4378 about 32 MiB more, and the engine cannot tell the builds apart from the bytes. **Rebuild your components.** The default budget when `--resident-memory-percent` cannot be derived (the worker's memory cannot be read) is 8 runs of the dearest language, which is C# at 59 MiB again, so 472 MiB.
