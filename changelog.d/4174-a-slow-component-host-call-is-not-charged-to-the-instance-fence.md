- **FIX: a Python or C# workflow whose host call took longer than `--wasm-instance-timeout` was killed (cleat#4174).** A durable call, a plugin call or a streaming plugin call that spent more than 30 s (the default) waiting in the host, an LLM call or a slow API for example, failed the run with `execution time limit exceeded (30s wall-clock budget; configure with --wasm-instance-timeout)`, against the flag's own help ("time the guest spends blocked in a host call ... is NOT charged"). Measured on a stock worker with one durable call to a service that sleeps and nothing else: a 25 s service completed, a 40 s service **failed after 44 s** with the call dispatched once and the service answering. The core-module path (Go) brackets host time (`hostBudget`) so the fence charges only guest execution; the component path (Python, C#) did not. It does now: one bracket in the component callback dispatcher covers every host import, as `hostFunc` does for core, and the guest's deadline is re-armed with what it has left when a host call returns. **The fence still kills a runaway guest**: a guest-side tight loop is killed at the timeout, with or without a host call before it (`TestASlowHostCallIsNotChargedToTheInstanceFence`). That test runs through a real worker with a 10 s fence and a 16 s host call (Python durable call, plugin call and streaming plugin call; a Go core control) and `TestCSharpASlowHostCallIsNotChargedToTheInstanceFence` does the same through a real C# component. **v0.4.0 and v0.5.0 are affected, by reading both tags' source** (their `engine/component_cgo.go` has no bracket and their core backend does); not executed there. A side effect, as on the core path: the guest's execution budget now starts when the guest starts running, not when the store is created, so time spent instantiating the component (CPython's own start-up, for Python) no longer comes out of it; instantiation still runs under the timeout as its own bound.
