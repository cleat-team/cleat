### 3.503 `workflow_defs.entry_point_schemas` had no `ISJSON` check on SQL Server — ✅ **FIXED 2026-10-13** (cleat#3355)

**Pre-existing, not a regression — and invisible until a different PR made the guard able to see
it.** `migrations/mssql/005_entry_point_schemas.sql` added the column as plain `nvarchar(max) NULL`
with no check, while PostgreSQL declares it `jsonb` (`migrations/postgres/006_entry_point_schemas.sql`).
Every other column PostgreSQL declares JSONB carries an `ISJSON` check on the SQL Server side; this
one was missed when it was added (cleat#1980) and stayed missed for the same reason
`TestMSSQLValidatesEveryPostgresJSONBColumn` didn't catch it: that guard parses JSONB columns out of
`migrations/postgres/001_schema.sql`'s own `CREATE TABLE` text, and the old postgres chain added this
column via a standalone `ALTER TABLE ... ADD COLUMN` in a later file — never part of 001's text, so
the guard's parser never saw it. WS-1's postgres consolidation (cleat#3346/#3347) folds that `ALTER`
into the generated baseline's column list, which is what made the gap visible: the guard **passes on
`origin/develop` blind, not green**, and would fail once postgres's `001_schema.sql` is consolidated.

**Confirmed independently before fixing, not assumed from the report.** Re-derived the column count:
`grep -in isjson migrations/mssql/001_schema.sql` (post-`#3349`-compaction baseline) finds 15 existing
checks, one per other JSONB-mirrored column; postgres declares 16 such columns once consolidated.
`entry_point_schemas` is the one gap.

**Fix:** a new `migrations/mssql/015_entry_point_schemas_isjson_check.sql`, guarded through
`sys.check_constraints` (the same shape `004_workflow_defs_exposure_class.sql`'s `CHECK` addition
uses, so a crash-and-replay re-run doesn't fail on "object already exists"):

```sql
IF NOT EXISTS (SELECT 1 FROM sys.check_constraints WHERE name = 'ck_workflow_defs_entry_point_schemas')
    ALTER TABLE dbo.workflow_defs WITH NOCHECK ADD CONSTRAINT ck_workflow_defs_entry_point_schemas
        CHECK ([entry_point_schemas] IS NULL OR isjson([entry_point_schemas]) = 1);
GO
```

`WITH NOCHECK` and NULL-tolerant for the same reason `ck_workflow_defs_dag_spec` (the other nullable
JSON column on this table) already is: existing rows predate the column's JSON-producing callers.

**Verified behaviorally, not just structurally — the lesson cleat#3346 had just surfaced about
`catalogdiff` applies equally here: a check that LOOKS present can still not fire.** Built a fresh
database from the real chain (001 through this new 015, via the production `migration.Runner`) and
ran live `INSERT`s with tenant session context set: invalid JSON (`N'{not json'`) rejected with
`The INSERT statement conflicted with the CHECK constraint "ck_workflow_defs_entry_point_schemas"`;
valid JSON and `NULL` both accepted. Also confirmed the guard's own matching function
(`mssqlHasISJSONCheck`'s `ALTER TABLE` scan) recognizes the new constraint's exact text shape against
a synthetic postgres block declaring the column `jsonb` — the guard will go green for real, not blind,
the moment the postgres side lands.

**Also fixed:** the guard's own failure message pointed readers at
`migrations/mssql/037_json_column_checks.sql` for a worked example — deleted by the earlier
`cleat#2434` compaction, a dangling pointer nobody had hit because the guard had never failed. Now
points at `ck_workflow_defs_dag_spec` in `001_schema.sql` for the shape and at this file for a current
worked example, with a note on why the old name is gone.

**Sequencing:** landed standalone, ahead of `#3349` (the mssql re-compaction), to unblock WS-1's
postgres consolidation as soon as possible rather than waiting on `#3349`'s own dependency on `#3353`.
`#3349` folds this file into the regenerated baseline like every other numbered file above it.
