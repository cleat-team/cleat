**Six generator bugs fixed, all one root cause: rewrites written for cleat#2059's one-time
historical transition, never re-tested against their own already-transitioned output.**

The first four, found by iterating the generator against the correct core-only dump until it ran
clean:
  - the "no hardcoded schema" self-check flagged a quoted STRING LITERAL (`'public'` inside
    005's `CHECK (exposure IN ('public', 'auth', 'internal'))`, which pg_dump renders as
    `CHECK ((exposure = ANY (ARRAY['public'::text, ...])))`) as a schema qualifier — the same
    "a text search cannot tell a thing from a sentence about the thing" trap CLAUDE.md already
    names, here as a string value rather than a comment.
  - the `event_history` partition splice assumed an unpartitioned source, so it raised
    `ValueError` on a dump of an already-partitioned table (the committed baseline, re-run)
    instead of passing it through.
  - the primary-key rewrite assumed the pre-partitioning `(workflow_id, step)` shape was still
    present to replace; an already-partitioned source carries the new `(tenant_id, workflow_id,
    step)` shape, with no predecessor left to rewrite FROM.
  - the dead-index removal (`idx_event_history_tenant_wf`, now redundant with the moved PK)
    asserted exactly one match; the prior compaction had already dropped it for good, so a
    second run correctly finds zero and must not treat that as an error.

**A fifth and sixth, found only by a clean `TestCascadeDelete/postgres` failure** (`pq: no
partition of relation "event_history" found for row`) **after the first four were fixed and
every structural check had already passed — the structural diff could not see this one.** The
dump source (genuinely partitioned by the time it's dumped a second time) carries real
`event_history_p0`.._p63` objects that pg_dump splits into `TABLE` / `TABLE ATTACH` / `ROW
SECURITY` / `POLICY` entries. The generator's `TABLE`-passthrough bucket kept the bare,
unpartitioned `CREATE TABLE` for each child untouched, while unconditionally synthesizing its own
correct `CREATE TABLE IF NOT EXISTS ... PARTITION OF ... FOR VALUES ...` for all 64 children
later in the file. The passthrough version runs first and wins (`IF NOT EXISTS`), so every
partition ends up a bare, unattached table and every `event_history` insert fails. A second,
unguarded `CREATE POLICY` duplicate for the same 64 children existed in the same shape and would
have failed outright (`42710`) once the first bug was fixed. Both fixed by stripping the
passthrough per-child entries from the `TABLE`, `ROW SECURITY`, and `POLICY` buckets before the
synthetic ones are added.

**Why `catalogdiff` didn't catch the fifth/sixth bug, and the generalisable point:** the
differential compares catalog STRUCTURE — does a table named `event_history_p0` with the right
columns exist on both sides — not whether it is genuinely attached as a partition. Both the
broken and the fixed baseline have a table of that name and shape; only a live `INSERT` exercises
the attachment. Same shape as this file's own standing lesson about a check that cannot see what
it is not looking at, arriving through a tool rather than a test.

**One more guard needed a fix, not from this bug but from the SAME consolidation:**
`migration/migrations_do_not_hardcode_the_schema_test.go`'s allowlist for cleat#1986's exposure-
class `CHECK` was keyed on the pre-dump source text (`CHECK (exposure IN ('public', 'auth',
'internal'));`); the consolidated file carries pg_dump's rendering instead
(`CONSTRAINT ck_workflow_defs_exposure CHECK ((exposure = ANY (ARRAY['public'::text, ...])))`),
which the exact-string allowlist did not match. Added the new rendering as its own entry,
falsified both ways (restored a genuine violation elsewhere in the file to confirm the guard still
fires; confirmed the new entry's removal makes the original failure return).

**A second, independent guard (`TestMSSQLValidatesEveryPostgresJSONBColumn`) went from blind to
red on the same consolidation — not a defect in this PR, but a pre-existing SQL Server gap the
guard could not see until now.** `workflow_defs.entry_point_schemas` was added to PostgreSQL via a
standalone `ALTER TABLE ... ADD COLUMN` (006, now folded in) that was never part of `001`'s
`CREATE TABLE` text on the pre-compaction tree, so the guard's table-block parser never saw it;
SQL Server's own column has carried no `ISJSON` check since it was added (cleat#1980) and nothing
since corrected it. Filed as cleat#3355, fixed by WS-4 in #3356 (§3.503) ahead of this PR, since
the guard adds no skip mechanism and this PR cannot go green without it landing first.

**`postgresProcedureMigrations` in `engine/store_backends_procedures_test.go` also needed

`021`) no longer exist, caught independently by both `applyPostgresProcedures`'s hard file-read
