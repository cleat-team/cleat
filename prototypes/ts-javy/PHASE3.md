## Findings

1. **Request bytes differ, and replay does not look at them.** The recorded request of `inventory.Reserve` is
   `{"cart":[{"sku":"SKU-001","quantity":2}],"user_id":"cross-test"}` from Go and
   `{"cart":[{"quantity":2,"sku":"SKU-001"}],"user_id":"cross-test"}` from both TypeScript and Rust (Go's differs in nested key order; my reading is that Go marshals struct fields in declaration
   order while the other two sort keys, which I did not confirm; `TestTSAndRustRecordTheSameRequestBytes` shows TypeScript and Rust
   agree). Two differences were reported (TypeScript against Go and Rust against Go, at event 0 only); no replay failed. This matches how the engine compares a replayed call (service, operation and type, not the
   request bytes) — **by reading and by this result, not by a test that changes only request bytes**. It matters for anything that
   later hashes a request.
2. **The TypeScript SDK had a canonicalisation hole and a swallowed exception, both found by this phase and fixed.** The result was
   serialised with raw `JSON.stringify` (key order and escaping differ from Go in the 7 categories above); and an exception thrown
   *while serialising* the result was dropped, so the module returned no result and the run ended with "returned no result". Results
   are now canonical by default and the serialisation error is reported (`could not return the result: …`; the `circular` error case
   shows the cause).
3. **NaN / ±Infinity: the SDK now matches Go (productisation item "TS SDK matches Go").** Go's `encoding/json` refuses them; JS
   `JSON.stringify` turns them into `null`, silently. The SDK's single encoder (`encode`, used for call, child, sideEffect and result
   payloads) refuses with Go's text. `NAN_POLICY=lenient` is the build switch for the red control. **Host side:** ABI.md §6.6 gives
   the matrix; I did not re-derive it.
4. **ENGINE behaviour, not a JavaScript issue: `[await_signals, X]` reads as "wait timed out".** When a recorded `await_signals`
   is followed by an event that is not `signal_received`, the engine treats the wait as timed out rather than refusing the history
   (`engine/signaller.go`, cleat#947). I met it because my first red control retyped `signal_received` expecting a refusal and got
   none, in any language (the four `OBSERVATION` lines in `xlang-go-test.txt`: Go targets suspend, TypeScript targets error). The
   assertion I kept uses `child_workflow` retyped, which **is** refused (4 of 4). This is the engine's documented-by-issue behaviour
   and is recorded here so nobody reads the absence of a refusal as a JavaScript defect.
5. **Not an event: `DurableLog`** is not a history event, and `sleep` records none, so histories compared event-by-event have equal
   length across languages (4 events for `place_order`).
6. **The Rust run's log shows `step=4` where Go and TypeScript show `step=3` on the final log line.** Observed in the worker-style
   INFO output of the harness; **not examined** — it does not change the recorded events (shapes are equal) and is not a Q4 question.
7. **`event_count=7` and 2 warnings on one JS "kill at the child wait only" run** (cleat-review, at load ~32), against 6 and 1 on
   the Go twin. Checked only against the mechanism WS-cleat1 found for cleat#3779: each wake at an unresolved `await_child` adds 1 to
   `event_count` without a new row, so an extra wake under load gives 7. I did not reproduce the 7. In this run's unloaded
   `warn-bisect.txt` all five variants (no kill, kill at the signal wait, at the child wait, at both, again) give **6 and 1**, and the
   Go control `go-control.txt` gives 10/10 vs 10/10 with the warning.

## Harness: isolation, and the defects it replaced

Phase 1 and 2 evidence had been produced while worker processes from earlier scripts were still alive. They claimed later runs and
wrote their log lines to files the counting script did not read, which gave a wrong "3 of 5" (Phase 1), a Go control of 0 of 10, and a
claims count of 0. Now:

- one pidfile per worker; `stop_stale()` kills only a pid whose command is **this checkout's** binary and then verifies, by a
  path-scoped `ps`, that none is left (else UNMEASURED); `Worker.start()` refuses if `/healthz` already answers (the message says how to
  choose another port); `atexit` stops it; `phase2-verify.sh` checks for a leak after every step (rc 3).
- Every setting is an environment variable (`CLEAT_PROTO_API_PORT`, `_PG_HOST/_PORT/_DB`, `_PG_CONTAINER`, `_KEY_FILE`), so a reviewer's
  run does not share a database or a port with mine.
- `harness_selftest.py`, **9 of 9**: a foreign process is spared; my own pidfile worker is stopped; an unrecorded process of my own
  binary is refused as UNMEASURED; a pidfile naming a foreign pid kills nothing; a busy `/healthz` refuses to start.

## Not measured (limits of this phase)

- A child that is **still running** when the parent is replayed and then finishes: the in-memory child store of the in-process harness
  cannot model it. Child *wait* suspension and its tamper are covered; "running, then finishes across a language change" is not.
- Two machines or two users: cross-language was one machine. The plugin-hash check is two directories, one user.
- Request-byte-only tampering (finding 1 is by reading plus the observed difference).
- `await_signals` followed by a non-signal event is an engine observation, not asserted (finding 4).
- The host-side NaN matrix (ABI.md §6.6) was not re-derived.
- Phase 0 was not re-run (see the top).
- Linux/x86 Javy pin; the macOS arm64 pin is the only one checked.
