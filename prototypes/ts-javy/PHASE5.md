## Q6 — does real-world TypeScript work?

> Bundle 4 common npm packages into a workflow. Pass line: **≥ 3 of 4 run unmodified; failures explained.**

**Met, with a finding that matters more than the count.** All four packages bundle and run **unmodified** (no patch to any package, no
polyfill added), and every divergence below has a mechanism. But **two of the four produce a silently wrong answer** — no error, a plausible
value — and those are the result to take away.

Each case runs the same function in the guest and in Node, and the harness compares canonical JSON. `control_differs` is a known-positive: it
returns `typeof process`, which differs by construction, and it reported DIFFERENT for **4 of 4** packages, so the comparator can say
"different". Every case was also replayed and re-run later: `replay-stable` and `later-same` were `True` for every case of every package,
including the ones that are wrong, so the wrong answers are **deterministic**, not flaky. (`evidence/phase5/npm.txt`, `npm.json`.)

| package | version | cases (excl. control) | equal to Node | not equal |
|---|---|---|---|---|
| `zod` | 4.6.7 | 7 | 5 | `string_formats` (silent), `url_global` (the cause) |
| `date-fns` | 4.4.0 | 8 | 6 | `parse` (silent), `native_date_setter_nan` (the cause) |
| `lodash-es` | 4.18.1 | 6 | 5 | `debounce` (loud) |
| `uuid` | 14.0.3 | 6 | 4 | `v4`, `v7` with no options (loud) |

**Loud** (the guest throws, the run fails, the author sees it):

- `lodash` `debounce`: `ReferenceError: setTimeout is not defined`. There are no timers in the guest, by design (a timer is not a durable
  operation). The rest of lodash-es (collections, objects, strings, `template`, `random`) matches Node.
- `uuid` `v4()` and `v7()` with no arguments: `ReferenceError: crypto is not defined`. They read `crypto.getRandomValues`. With the
  `random` option supplied (`v4_with_random_option`, `v7_with_options`) they are **equal** to Node, and `v3`/`v5`/`parse`/`stringify` are
  equal. The workable pattern is to take randomness from the SDK (`ctx.random()`, which is derived and replay-safe) and pass it in.

**Silent** (no error; the answer is wrong):

- `zod` `z.url()` reports a valid URL as **invalid** (`url:false` where Node says `true`). Cause (`url_global`): zod's validator does
  `new URL(...)` inside a `try/catch`, the guest has no `URL` or `URLSearchParams` (`["undefined","undefined"]`), and the `ReferenceError` is
  swallowed by that `catch`. `z.uuid()`, `z.ipv4()` and `z.iso.datetime()` agree with Node.
- `date-fns` `isValid(parseISO("nope"))` is `true` in the guest and `false` in Node, and `parse("29/02/2024", …)` is fine. Cause
  (`native_date_setter_nan`, no package in the way): QuickJS's `Date` setters return `NaN` for a non-finite argument **but leave the date
  unchanged**, where the spec makes it an Invalid Date. `new Date(0).setUTCFullYear(NaN)` stringifies as `Thu Jan 01 1970` in the guest and
  `Invalid Date` in Node. date-fns builds its dates with `setUTCFullYear`, so an invalid ISO string comes back as 1970-01-01. The cause is in
  the engine's `quickjs.c` (`set_date_field`: `if (!res) return JS_NAN;` before the time value is stored); I read it, I did not patch or
  report it upstream. Everything else date-fns does here (format, arithmetic, intervals, distance, the German locale, and the `distanceToNow`
  that depends on the date shim) matched Node.

**What this says for the decision.** The packages that fail loudly are an inconvenience with a known workaround. The two silent ones are a
correctness hazard in a *durable* engine: a workflow that validates a URL with zod, or treats an unparseable date as valid, behaves
differently from the same code under Node and the author gets no signal. Both are fixable in the runtime (provide `URL`; fix the setter
semantics), neither is fixable by the workflow author, and the shipped product would want a **conformance list** of known divergences. I did
not look for further silent divergences beyond these 28 cases, so there may be more.

(1,226,974), lodash-es 1,306,148 B (1,211,306), uuid 1,164,092 B (1,140,735). The module is the ~1.07 MB Javy plugin plus the bundle, so the

## Q7 — is it workable day to day?

> `cleat build --target ts`, error messages, stack traces mapped to `.ts` lines. Pass line: **a thrown error names the `.ts` file and line.**

**Met.** `evidence/phase5/srcmap.txt`: **15 of 15 verdicts**; `evidence/phase5/cli.txt`: **10 of 10 verdicts**.

- A throw in the user's code names `workflows/srcmap/srcmap.ts` at the throw line and at the call site, and **no bundle position
  (`function.mjs:NNNN`) is left** in the message. This holds when the throw happens before any host call and after one (`srcmap_late`).
- A library frame is mapped too: a `uuid` error names `node_modules/uuid/dist/parse.js:4:15`, not a bundle offset. A zod error names the
  user's `.parse` line.
- The message text before the first stack frame is byte-identical with and without maps, so the maps cost nothing in what an error *says*.
- **Known-negative for every case:** the build without maps names only `function.mjs:<bundle line>`, so the mapped result is not the default.
- The column is what QuickJS reports for the frame (the `new Error(` position), not the `throw` keyword (col 3 vs col 29 in the case above);
  lines are exact.

**Cost of the maps** (`srcmap.txt`): the map payload is 451,785 B for the test module; as a share of a module it is +0.5 % (a small
workflow) to +7.8 % (lodash-es) to **+29.1 % (zod)**. The map is embedded in the module and read only on failure.

**`cleat build --target ts`** (`cmd/cleat/build_ts.go`, 10 of 10 CLI verdicts): it builds a workflow **outside the repository** and writes the
module to `-o`; stamps the language label and the engine pin; the deployed workflow completes with the right result and an invalid input
fails with a mapped error naming `src/orders.ts` relative to the source root (the caller's working directory); a malformed entry name is
refused (exit 1) before any build; a source the static determinism check refuses exits 1 and emits **no artifact**; a missing toolchain is
**UNMEASURED, exit 2**, saying what is missing (not a failure of the source). `TestParseTSEntry` and the other unit tests pass, and a mutant
that accepts a bad entry spec fails exactly the three cases it should (`wf.ts:`, `wf.ts:PlaceOrder`, `wf.ts:place-order`), with the restore
checked by content.

## Defects found and fixed on the way (not obvious from the code)

- Source-map paths differ between `/var/…` and `/private/var/…` on macOS; the Python side and the Go side each needed `realpath` /
  `EvalSymlinks` normalisation, or a source file outside the repository got a path with the wrong prefix.
- An earlier CLI verdict matched an ugly path *tail* and would have passed with a wrong source root. It now asserts the **whole path**.
- zod's `ZodError` carries no library frames in its stack, so the library-frame case uses `uuid`, whose error does.

## Not measured (limits of this phase)

- Other packages: anything that needs `URL`, `TextEncoder`, `Buffer`, `fetch`, timers, `crypto` or `process` fails or diverges the same way;
  I tested those globals through the four packages above, not each one.
- A Windows or Linux build, a second Node version, or any machine but one macOS arm64 host.
- The cost of source maps in the **deployed row** (compressed) and on **load time**; only module bytes are reported here.
- Whether a developer *likes* it: Q7 is measured as "the error names the line", which is necessary, not sufficient. No editor integration, no
  debugger, no `cleat dev` loop.
- Dynamic mode, at all (blocked, see PHASE1.md). StarlingMonkey was skipped by decision (coordinator, 2026-11-13); the two silent divergences
  above (`URL`, `Date` setter) are exactly the kind of thing a fuller engine might fix, which is the condition PHASE4.md set for revisiting it.
