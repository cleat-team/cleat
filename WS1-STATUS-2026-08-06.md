### #345 — an administrative principal under RLS (§3.37)

SQL Server applies a security policy to **every** principal, `sysadmin` and `dbo` included.
Measured: connected as `sa` with no session context, a table holding three rows reads as empty.
So there was no connection that could see across tenants — not for a support query, a
cross-tenant backfill, or test teardown.

PostgreSQL never hit this because a superuser bypasses RLS unconditionally, which is why
`005_app_role.sql` argues the *opposite* case (keep `cleat_app` out of that exemption). That
design has two halves; SQL Server inherits the restricted half free and cannot inherit the
privileged half at all — the predicate is the only place an exemption can live.

`migrations/mssql/012_admin_role.sql` creates an empty `cleat_admin` role and adds
`OR IS_ROLEMEMBER(N'cleat_admin') = 1` to `fn_tenant_filter`.

Safety properties, all verified against SQL Server 2022:

- ships with **no members** — applying it changes nothing until a deployment grants it;
- `db_owner` does **not** confer it: `sa` reads `IS_ROLEMEMBER = 0` and stays filtered, so
  "the app connects as sa" does not silently lose isolation;
- `dbo` **cannot** be added — SQL Server refuses outright.

The second decided the design. Had `sa` been exempt, this would have disabled tenant isolation
for the default deployment the moment it applied.

**Cost, measured** (50k rows, 300 queries, two interleaved rounds): point lookups unchanged
(~350 µs); full scan 3.4 ms → 4.1 ms, **+20%**, tracking rows scanned at ~14 ns/row.
`IS_ROLEMEMBER` is not folded to a per-query constant. Two rewrites were tried and both were
worse (role-first +33%, scalar subquery +166%), so the shipped form is the cheapest of the
three. Recorded in the migration header so nobody re-measures it.

**Review-worthy judgement calls in this PR:**

1. Accepting a 20% full-scan regression. Justified because point lookups — the store's dominant
   access pattern — are unaffected, and the alternative is no administrative path at all. A
   reviewer could reasonably want this behind a flag, or want `ListWorkflows` measured
   specifically rather than a synthetic scan.
2. Three of the four tests pass with **and** without the fix, by design — they are guards that
   nothing else moved, not regression tests. Only
   `TestMSSQLAdminRoleSeesAndDeletesAcrossTenants` discriminates (falsification confirmed: with
   the `OR` clause removed it alone goes red).

### #333 — the test schema switch (§2.71)

Runs `engine/testutil`'s SQL Server schema from the shipped migrations instead of 334
hand-written lines that had drifted. **141 failures → 9**, in three measured steps against a
freshly recreated `cleat_real`:

| step | failures |
|---|---|
| starting point | 141 |
| teardown deletes via an admin connection (`testutil.MSSQLAdminDB`) | 58 |
| `mssqlSchemaFiles` applies `012` | 39 |
| the store is built the way production builds it | **9** |

The third step is the substantive finding and is **§1.3-shaped, not a fixture problem**:
`NewMSSQLStore(db, ...)` on a plain pool puts `sp_set_session_context` on none of its
connections, so under the shipped policies **the store cannot see rows it just wrote**. Every
non-test caller uses `NewMSSQLStoreFactory().OpenStore()` — `cmd/cleat-worker`,
`cmd/cleat-bench`, `cmd/deploy-workflow` — and that is what wraps the connector. The tests were
exercising a construction nothing ships, and it passed only because the hand-written schema had
no policies to enforce.

**Worth deciding in review:** `NewMSSQLStore` is exported. An embedder handing it a plain pool
gets a store that silently sees nothing under RLS. Options: document it, make it refuse a pool
without a tenant connector, or unexport it. Not decided here.

## 4. Outstanding, decision-first (not started, deliberately)

These need an owner's decision, not code. Each was escalated rather than guessed at.

1. **§1.7 residual — MySQL has zero RLS policies.** Go-level `WHERE tenant_id = ?` is the
   entire isolation. Options: a view layer, a connection-user scheme, or documenting MySQL as
   single-tenant-only. This is the largest hole in the workstream's theme and nothing has been
   done to it.
2. **§3.12 residual — `workflow_defs` is a global namespace.** Fixing it means a composite key,
   3 FKs per dialect, and ~96 query sites. Large, mechanical, and needs sign-off before starting.
3. **§3.35 — re-acquiring a concurrency key you already hold** returns `true` on MySQL and
   `false` on PostgreSQL/SQL Server. A decision about whether the primitive is re-entrant.
4. **§3.38 — `TestAdminForceResolve_*` failed once, unreproduced.** Three tests failed in a
   PostgreSQL-only engine run that followed a three-dialect run against the same shared
   database. Clean `develop` and the branch both give 0 failures on the same command, so it is
   cross-run state, not a code defect. Recorded as a hypothesis, not a diagnosis — one failing
   observation against two passing ones.
